# poimen

A desktop app for AI coding agent sessions: watch and steer your terminals and agents with editor tabs, menus and a status sidebar. poimen ships its own terminal server (`poimen-server`), so no other tool is needed.

*Poimen* (ποιμήν) is Greek for shepherd. `poimen-server` keeps the herd; poimen is the window you watch it through.

Site, downloads and the user guide (getting started, spaces, agents, GitHub, runs, remote machines, console and MCP, settings): <https://gravionlabs.github.io/poimen/>. This README is the detailed reference.

> **Status: early.** poimen is in daily use and released regularly, but it still changes quickly. Expect rough edges.

## How it works

```
┌──────────────── poimen (Tauri) ────────────────┐
│ sidebar: spaces / terminals / agent status     │ ◄── events.subscribe (server.sock)
│ tabs: one xterm.js for the active tab          │ ──► requests, terminal.attach
└───────────────┬────────────────────────────────┘
                │ one socket under the runtime dir
                ▼
          poimen-server  (owns the PTYs, one per user, started by poimen,
                          outlives the app; agent status from Claude Code
                          and Copilot hooks)
```

- **`poimen-server` is the default backend.** The release bundles it next to the app (`externalBin`), poimen starts it detached when nothing answers and stops it only after your confirmation (restart of an outdated server, "Quit poimen and stop server"). Closing poimen, or closing a tab, only closes the view; the terminal and its agent keep running. The protocol is in [docs/protocol.md](docs/protocol.md), the setting is `backend` (see "Settings").
- **Windows.** The Windows x64 installers run the same backend: `poimen-server.exe` listens on a named pipe instead of a Unix socket, terminals run through ConPTY (`pwsh`, else Windows PowerShell, else `cmd.exe` by default), and its state lives in `%LOCALAPPDATA%\poimen-server`. The hooks run through PowerShell there. Windows support is new and covered by CI (`windows-latest`); a hands-on check of a released build follows in [#417](https://github.com/GravionLabs/poimen/issues/417). Start poimen normally, not as administrator. Known limitations are in the [installation guide](https://gravionlabs.github.io/poimen/guide/installation#windows-x64).
- **Agent status needs hooks.** Claude Code and GitHub Copilot CLI report working, blocked, error and done through hooks (`Stop` / `agentStop` report done, which stays until the next prompt; `SessionStart` reports idle; `PermissionRequest` / `permissionRequest` report blocked with the tool; `StopFailure` / `errorOccurred` report error, a failed turn, which counts as waiting like blocked until the next working report; `PostToolUseFailure` and `PostToolBatch` report working again) that call `poimen-server hook`. Claude Code gets the newer events only when its installed version knows them (`claude --version`); after a Claude Code update, *Repair* in Settings › Backend › Server adds the missing ones. On the first start with the poimen backend, poimen offers to install them when they are missing (an *Install hooks* button runs `poimen-server integration install` for the agents without them; *Not now* is remembered in the UI state). You can do it by hand any time: `poimen-server integration install|uninstall|status claude|copilot [--settings <path>]`. An agent reads its hooks when it starts, so one that already ran needs a restart. A hook that cannot report writes the reason to `hooks.log` next to the server's `server.json` (Windows: `%LOCALAPPDATA%\poimen-server\hooks.log`). The server's own diagnostics go to `server.log` in the same directory and the stderr of each terminal's PTY host to `hosts/<terminal id>.log` (see `docs/protocol.md`, "Log files").
- **Inline images.** Terminals show sixel and iTerm inline images (`@xterm/addon-image`, limited to 16 Mpixel per image and 32 MB stored). The Kitty graphics protocol is not supported by that addon version. Images are live only: the server's terminal emulator keeps no graphics, so after a reattach or an app restart the cells where an image was are blank. Images are not shown in the `poimen` TUI.
- **Claude Code's classic renderer.** Terminals measure characters with Unicode 11 widths (emoji such as `✅` and `🚀` take two cells), like the server grid and Claude Code, so Claude's frames line up. Changing `/tui` while Claude runs, or narrowing a pane under the classic renderer, can still stack frames on top of each other in any terminal: Claude moves up by the rows it counted before the reflow. Restart Claude or press `Ctrl+L` to redraw.
- **Tokens from scripts.** Tools inside a poimen terminal (the deliver loop, your scripts) can show their state in the sidebar rows with tokens: `poimen-server report tokens [--terminal <id>] [--ttl <s>] [--source <s>] name=value ...` (names of 1 to 32 ASCII letters, digits, `_` or `-`, at most 16 per call; `name=` with an empty value removes the token; the TTL applies to that call; `--source` defaults to `cli`) and `poimen-server report clear --source <s>` (removes everything that source set). Without `--terminal` it uses `POIMEN_TERMINAL_ID`, which every poimen terminal sets; outside one, or with no server running, it does nothing and exits 0 (only a usage error exits 2). The tokens appear as `$<name>` in `sidebar.rows` (for example `$deliver_step`). For an agent without hooks: `poimen-server report agent --state working|blocked|idle --source <s> --agent <name>` sets its status.

### The app

- **`poimen-server` is the backend.** Closing poimen, or closing a tab, only closes the view; the terminal and its agent keep running. The `poimen` console (TUI and CLI) works next to the app.
- **Input by default.** A pane opens for input: poimen first attaches as the controller without a takeover and, as the only controller, sets the terminal size itself so the output width follows the window. If another client already holds the controller (for example the `poimen` console), the tab falls back to an observer (read-only) and says why, with an explicit *Take over* button (never automatic). The flat mode button in the status bar (text `Input` or `Read-only` with a pencil or lock icon; the tab shows `RO` or `IN`) toggles between input and forced read-only per tab while it is open; it is dimmed and disabled while another client controls the terminal. If another client takes the controller later, the tab goes read-only with a banner and going back to input stays your action. `terminal.autoControl: false` opens all tabs read-only again. In input mode the mouse goes to the pane application; Cmd+click (macOS) or Ctrl+click (Linux, Windows) on a link opens it in the default browser (URLs found in plain text lose trailing `. , ; : ' "` and an unbalanced closing `)` or `]`; `Foo_(bar)` stays whole), and Shift bypasses the forwarding for text selection (Shift+drag). xterm.js tracks the mouse modes itself: a plain drag goes to a pane application that asks for the mouse (for example Claude Code dialogs highlight the dragged cells), otherwise it selects; hold Shift to get xterm's own selection. Copy the selection with Cmd+C (macOS) or Ctrl+Shift+C, in input and read-only tabs (read-only tabs select with a plain drag). Paste with Cmd+V or Ctrl+Shift+V in input mode, as bracketed paste when the pane application asked for it. Files dragged from the OS onto a terminal type their paths, shell-quoted (single quotes; PowerShell quoting on Windows) and space-separated, as a paste in input mode; the terminal is highlighted while you drag over it. A read-only tab or a pane on a remote machine types nothing and says why in the status bar (the paths are local). Pasting an image (a paste with an image and no text) saves it as `paste/<unix ms>.<png|jpg|gif|webp>` in poimen's app cache directory (at most 20 MiB, other types refused, files older than 24 hours removed on each paste) and types its quoted path the same way; a read-only tab or a remote pane refuses it. The wheel scrolls the pane.
- **Editor tabs.** Opening a pane adds a tab to one tab bar above the terminal: a click opens a preview tab (italic, replaced by the next preview), a double click pins it, a second click on an open pane activates its tab. Tabs close with the x or a middle click and reorder by drag. Only the active tab of each group keeps a stream open; hidden tabs close theirs, the pane keeps running.
- **Split editor groups.** The tab context menu (right click) splits a tab right or down into a new group with its own tab bar; `Cmd+\` / `Ctrl+\` splits the active tab right, with Shift down. Drag a tab onto another group's tab bar to move it. Dividers resize by drag or with the arrow keys; each visible group streams its active tab and its terminal size is sent to the server when it changes. Closing the last tab of a group removes the group. A pane is open in one group at a time.
- **Angular frontend.** The UI is Angular 22 with helix-ui (light and dark follow the system); `src/app/core` is the bridge to the Tauri commands and events, `src-tauri` stays a thin shell ([ADR 0001](docs/adr/0001-frontend-stack.md)).
- **Spaces tree.** The sidebar is a helix `hx-tree` of workspaces and their panes (the tab is secondary text). A badge tells agents (by kind, e.g. `cl` for claude) from plain terminals (`>_`); each row shows the status dot, git branch (`wt` for a linked worktree), directory (`foreground_cwd`) and the status message, state label or integration tokens when present. The filter field matches name, agent, branch, tab, directory and text; arrow keys, Home/End and type-ahead navigate, Enter opens. Branch and worktree come from a read-only `git rev-parse` in the pane directory; dirty state and ahead/behind come from one `git status --porcelain=v2 --branch` (2 s limit), refreshed on window focus, when an agent finishes and every 60 s while the window is focused.
- **Layout.** An activity bar (Spaces, Explorer, Notifications, GitHub, Runs) sits left of a sidebar you resize by dragging its edge (arrow keys work too) and toggle with `Cmd+B` (`Ctrl+B` elsewhere). Width and collapsed state persist in poimen's own UI state (webview local storage, not the user settings file), and so do the open tabs, active tab, editor groups and split sizes: poimen reopens as it was closed, and tabs whose pane or terminal no longer exists on the server are dropped with a notice; the layout works from 720 px window width. The Notifications view lists the last 100 agent status changes (blocked, done) of all spaces, newest first, with time, tab and message; a click opens the tab and marks the entry read, "Mark all read" clears the unread marks. The list lives in memory for the session only (the server sends no separate notification message, so entries derive from status changes).
- **Toolbar.** A thin bar at the top has a flat theme button on the right (icon and text: auto, sun or moon for `system`, `light`, `dark`). A click cycles system → light → dark; the tooltip and accessible name read like `Theme: system (click for light)`. The choice is written to the `theme` entry of `config.json` (other keys and comments stay) and applies at once; `system` follows the OS appearance live, and an external edit of the file updates the button.
- **Status bar.** The bottom bar shows the server connection (connected, reconnecting when the event watcher lost the server, unreachable when a snapshot read failed, each with the reason), the count of waiting (blocked) agents (a click opens the next one) and the active tab: pane id, the mode button (input, or read-only with the reason when another client controls the pane) and terminal size.
- **Events are invalidation signals.** Every server event triggers a debounced re-read of the space, tab and terminal lists. `agent.status_changed` is applied right away.

### Creating, splitting and closing panes

Panes are managed by `poimen-server`, so the result shows up through its events like any other change. The requests are listed in [docs/protocol.md](docs/protocol.md).

- **New space**: the "+" button in the Spaces header opens a dialog with a directory field (completes directories as you type), a Browse button (native folder picker) and a label (default: the directory name). It creates a space on the backend (`space.create`) and focuses it. A space that already has a pane inside the directory, else one labelled with the directory name, is focused instead and nothing is created. A label that another space uses falls back to the path relative to the home directory. A missing directory or a failing backend call shows the error in the dialog.
- **Close space**: right click a space in the sidebar and pick "Close space", click the x icon left of the chevron on its row (shown on hover, keyboard focus and for the active space; Tab reaches it, Enter or Space triggers it, and it neither selects nor collapses the row), or run "Close Space" in the command palette (closes the space of the active tab). It closes the space on the backend (`space.close`) and ends every pane in the space, so a space with panes asks for confirmation (pane and agent count) and an empty one closes right away. The tabs of its panes close, and the neighboring space is focused. The backend's error is shown when the close fails and the space stays.
- **New terminal**: File > New Terminal (`CmdOrCtrl+T`), or right click a workspace in the sidebar. A dialog asks for the directory (the workspace's pane directories are suggested; empty uses the backend's default: the space directory on poimen-server). It creates a tab in the workspace (`terminal.create`) and opens it.
- **Split**: right click a pane in the sidebar (Split right / Split down), or its tab (New pane to the right / below). The new shell starts in the pane's directory (`tab.split`).
- **Close pane**: right click a pane in the sidebar or its tab (Close pane). It always asks first and warns when an agent is working or waiting (`terminal.close`). It ends the whole terminal: the shell and every process of its session (background jobs, dev servers) get SIGHUP and, after 5 s, SIGKILL (Windows: the terminal's job object is terminated); a process that left the session (`setsid`, a daemon) stays, as in any terminal. Closing a tab with the tab's own Close entry still only closes the view.
- **Start agent**: right click a pane in the sidebar or its tab (Start agent...). A dialog asks for the agent kind, an optional name (defaults to the kind) and optional arguments (split on spaces); the pane has to be at its shell prompt.
- **Rename**: right click a pane (Rename... / Rename pane...). Renaming sets the name of the terminal; an empty name clears it.
- **Send a prompt**: a read-only agent tab has a one-line input above the terminal (it is hidden while the tab controls the terminal, where you type into the terminal directly; the typed text is kept). It waits for the agent to start working (or block), so it needs no controller and works in a read-only tab. It reports a stalled agent and an agent that waits at an approval (nothing is sent); the text is kept after a block.

### Agents

The step that installs the hooks (the *Install hooks* button, or `poimen-server integration install claude|copilot`) also registers `poimen mcp` ([ADR 0012](docs/adr/0012-mcp-server-for-agent-sessions.md)) as an MCP server of the agent, so a session can look around in poimen. Claude Code gets the entry `mcpServers.poimen` in `~/.claude.json`, Copilot CLI in `~/.copilot/mcp-config.json` (`poimen-rc` on a pre-release build, which runs next to the stable one without touching its entries). The one consent covers both; an agent that is already running reads its MCP config when it starts. The read tools:

- `list_spaces`: the spaces of the server with their tabs.
- `list_terminals`: the terminals, with the agent status and the space of each.
- `whoami`: the terminal the agent runs in (`POIMEN_TERMINAL_ID`); `{in_poimen: false}` outside poimen.
- `list_runs`: the agent runs of a repository (`repository` directory), read from its `.agents/events` files.
- `start_agent` (`harness`, `space?`, `model?`, `prompt?`, `name?`): a new terminal running a harness of your `harnesses` config.
- `prompt_agent` (`terminal`, `text`): types a prompt into the agent of a terminal, refused while it works or waits.
- `wait_agent` (`terminal`, `timeout_s?`): waits until the agent of a terminal is done, blocked, in error or gone, or the timeout (default 300 s, at most 3600 s) passed; answers with the status and, when blocked, the notification text. Read tool; it includes the agent's report when there is one.
- `report_done` (`outcome`, `summary`, `files?`): an agent that was started with `start_agent` calls it once at its end (`start_agent` adds a short preamble with this rule to the prompt). poimen stores the report on the terminal, types one line (terminal and outcome) into the starting agent when it is idle (it waits while it works), and the Runs view shows the outcome and summary as the finished run.
- `read_agent` (`terminal`): the last assistant message of the agent's transcript (Claude Code and Copilot CLI) with the session id; an error when the terminal has no agent transcript. Read tool, also for a terminal on a remote machine.

To lead other agents with these tools (when to split, one worktree per worker, wait instead of polling, a blocked worker) install the short `poimen-lead` skill of [GravionLabs/skills](https://github.com/GravionLabs/skills/tree/main/skills/delivery/poimen-lead); it needs no CLI.

The write tools act freely in the space of the agent that calls them. For any other space poimen asks you in the app (who asks, what, where) and the call waits up to 60 s; declined, no answer, poimen closed or an agent outside a poimen terminal are refused. Every write shows in the notification center with the calling terminal.

The entry needs the `poimen` binary next to `poimen-server` or on `PATH`; without it only the hooks are installed and the status says `mcp: unavailable`. Settings > Server shows the state per agent. To remove the MCP entry together with the hooks run `poimen-server integration uninstall claude|copilot`; only the entry marked as poimen's (name, `mcp` argument and binary) is removed, any other `mcpServers` entry stays untouched.

## Requirements

- Nothing else to run: the installers bundle `poimen-server`. poimen starts it itself, see "Auto start" below.
- Coming from herdr? Remove its agent hooks with `herdr integration uninstall` (for each agent you installed them for) so they do not report next to poimen's.
- Rust 1.99.1, Node.js 26, pnpm

## Auto start

poimen pings the `poimen-server` socket at start (and on Retry); when nothing answers it starts the `poimen-server` next to the app executable, else the one found on the login-shell `PATH`, detached (own process group, no terminal), and waits for it up to 10 s. A server that answers is never restarted or stopped by poimen without your confirmation, and closing poimen leaves the server, its terminals and agents running.

Failures show in the sidebar as one message with the reason and a Retry button, which is there in every disconnected state (start failed, unreachable, reconnecting); there is no automatic retry loop. The start sits behind a `Backend` trait (`ensure_running`, `src-tauri/src/backend.rs`).

The menu bar has File (new terminal, close tab), Edit, View (sidebar, output panel, split, zoom, refresh), Go (command palette, next waiting agent, tab switching) and Window. Defaults follow VS Code; `CmdOrCtrl` is Cmd on macOS and Ctrl elsewhere. Every shortcut can be changed in the settings file (see below).

| Close all tabs | `closeAll` | CmdOrCtrl+Shift+W |

The command palette is a compact popup (480px, no dimming, a click outside closes it) centered on the editor area rather than the whole window; without an open tab it is centered on the window. It follows a window resize, a sidebar toggle or a panel change (such as the output panel) while open, stays inside the window, and its top edge stays put while the list filters. It is styled after JetBrains "Find Action": each row shows the title (the characters your query matched are highlighted), and the shortcut as a key cap. With an empty query the list is grouped under "Recent" (the last 5 entries you ran, kept in the window layout UI state), and "Poimen"; with a query it is one ranked list. Arrow keys skip the headings; Enter runs, Esc closes.

While a terminal has focus, only shortcuts that use Cmd are captured; every other key (Ctrl combinations on Linux and Windows included) goes to the program in the pane. Use the menu, or bind a `Cmd+` (Super) shortcut, to reach an action from a focused terminal there.

### Token totals in the sidebar

Every agent pane whose agent has a transcript (Claude Code, Copilot CLI) shows the tokens its session has used: hover the row for input, output, cache read and cache write (compact, `12.3k`); the space row shows the sum of its panes (`1.2M`). A usage-only reader follows each session file with one `notify` watch (no polling; for Claude the main transcript and the subagent files, each message id counted once), a pane on a remote machine through `agent.transcript` (no total while the machine is not connected). A pane without a transcript (plain shell, `gemini`, `codex`) shows none, and a malformed line is skipped. No cost in currency.

### Output panel (subagent transcripts and flow)

A panel below the editor area (View > Toggle Output Panel, the Output button in the top bar, `CmdOrCtrl+J`) shows what the subagents of a Claude Code or GitHub Copilot CLI agent are doing. They do not write to the terminal, so poimen reads the agent's session transcripts, read-only. For Claude Code: the session id and directory come from the backend (from the agent report of the server's hooks), the files from `~/.claude/projects/<directory with every non-alphanumeric character as "-">/<session>.jsonl` and `<session>/subagents/agent-<id>.jsonl` plus its `.meta.json` (type, description, tool use id). The panel follows the active tab's agent; its dropdown lists the subagents (description, type, running or done, duration) and the selected one streams its prompt, messages, collapsible tool calls with results and the final report. It scrolls along until you scroll up ("Resume auto-scroll" jumps back). A subagent is done when its meta says `finished` or the main transcript holds a final `tool_result` for its tool use id (the acknowledgement of a background launch does not count). For Copilot CLI, the session id comes from the backend the same way (`agent: "copilot"`) and the only file is `~/.copilot/session-state/<session>/events.jsonl`: one event per line, the subagents in the same file (their events carry an `agentId`). A `skill` call is shown as a skill, a `task` call as a subagent call (`subagent.started` links the subagent to it by `toolCallId`), and a subagent is done at `subagent.completed` or `subagent.failed` (the immediate result of a background `task` does not count); a subagent's messages come from its `user.message`, `assistant.message` (text, reasoning, tool requests) and `tool.execution_complete` events. The backend watches the files with `notify` and pushes `subagents` events (no polling); only an open panel watches. Other agents (`codex`, `gemini`, ...) and plain terminals show an empty state. Both transcript formats are internal to their agents: unknown entry or event types and fields are skipped. Visibility, height and tab are UI state (`core/ui-state.ts`); the panel has two tabs, Output and Flow. Not covered: Codex and other agents, Copilot sessions in VS Code, remote machines.

The **Flow** tab draws the run as a graph, laid out automatically (left to right by default, or top to bottom; no manual placement): the main agent, every `Skill` call (skill name and arguments) and every subagent (description and type), with edges in call order from caller to callee. Subagents that overlap in time (parallel) sit side by side; a subagent that calls skills or further agents nests them under itself, found by the tool use id of the call (a subagent whose call is not known is placed by its `spawnDepth`; for Copilot CLI it is derived from the `task` call that spawned it). The main node is labeled with the agent (Claude Code or GitHub Copilot CLI). Each node shows its status (running nodes are highlighted, done, failed), its duration (live while running) and, for agents, how many plain tool calls (Bash, Edit, ...) it made; those calls are counted, not drawn. A skill counts as done once its call has a result, so its duration is the call, not the work that follows. Claude Code nodes also show their tokens: total input (input + cache read + cache creation) and output, compact (`12.3k`), from `message.usage` of the assistant records, live while the node runs. The main node adds the context fill at its latest message; a skill or subagent node adds the context fill when it started ("at that time"). The node tooltip lists the four counts and the model the transcript names. A skill's tokens are the main (or calling) agent's messages between its call and its result; a subagent's come from its own `agent-<id>.jsonl` and are not counted again in the parent; a message written in several lines counts once. A missing or malformed `usage` is unknown: without usage data (a Copilot CLI pane, whose log has none) the row is hidden, never zeros. No cost in currency. Clicking a subagent node opens its transcript in the Output tab. The canvas supports zoom (buttons with zoom out left of zoom in, Ctrl+wheel), pan (drag), fit, a minimap and a layout direction toggle (left to right or top to bottom, kept in the UI state), and keeps its view while new nodes appear; the graph is built by `@foblex/flow` and `@dagrejs/dagre`, loaded on first use of the tab.

Known limits of the Flow tab: skill nodes show no plain-tool count (the transcript cannot attribute tool calls to a skill); a skill's duration is only call to `tool_result`, so skills are rarely "running"; the main node has no duration; subagents whose call is unknown are placed by `spawnDepth`; "failed" comes from an error result of a skill call or an agent call (in the main transcript or nested in a subagent). The Flow tab (live updates without zoom/pan reset, click-to-open, minimap, fit) is unit tested but still needs a manual check in the running app.

### GitHub pull requests

The GitHub item of the activity bar (or "Open GitHub" in the palette) opens a "Pull requests" tab (ADR 0005, `src-tauri/src/github_pulls.rs`, `src/app/github/`). It lists the open pull requests of the GitHub repositories behind the spaces and the explorer roots, read with `gh` (one GraphQL query per repository, answers cached for 30 s): repository, number, title, author, draft, checks (passed / failed / pending), review state, size (+/-) and age. Filters: Review requested (me), Mine, All; a repository filter; a text filter over title and number. Rows are selected with the checkbox, Shift+click (range) or the keyboard (Up/Down, Space). "Open in browser" opens GitHub links only. It refreshes with the Refresh button and when the window regains focus, never faster than every 30 s. A repository that cannot be read (for example "Run `gh auth login`") shows its own message; the others are still listed. Needs the GitHub CLI.

The tab's **Issues** section (`src-tauri/src/github_issues.rs`, `src/app/github/issues*.ts`) shows the open issues per repository as a tree over GitHub's native sub-issues (`parent`): up to 300 issues per repository, newest updated first. The level comes from the label `epic`, `feature`, `pbi` or `bug`, else from a `[Epic]`, `[Feature]`, `[PBI]` or `[Bug]` title prefix. An issue whose parent is closed, not read or in another repository is a root; parent cycles are ignored (the issues on one become roots). Each row shows the level, number, title, `[needs-refinement]` and `[needs-decision]` markers, `[@assignee]`, sub-issue progress and the linked pull requests (closing references plus open pull requests on a branch `<type>/<nr>-...`) with their check counts; "Open" and the PR number open GitHub links in the browser. Filters: state (open or closed, which reads again), level, label, assignee and text; a match keeps its ancestors visible. Collapsed nodes are remembered per repository in the UI state.

The **Milestones** section (`src-tauri/src/github_milestones.rs`, `src/app/github/milestones*.ts`) lists the open milestones per repository, read through REST with the ETag cache. They are ordered by version: legacy `x.y.z` titles (an optional leading `v`) first, then `M<n>` and `M<n> (x.y.z)` by `n`, each numerically (1.10.0 follows 1.2.0, M10 follows M2); names that are no version come last. The current milestone is the lowest one that still has open issues. Each row shows the due date, the open and closed counts and a progress bar. Selecting a milestone filters the issue tree of that repository to it (select it again to clear the filter).

### Runs

The Runs item of the activity bar (or "Open Runs" in the palette) opens a "Runs" tab with the agent runs (deliver loops and sessions) of the repositories behind the open spaces (`src-tauri/src/deliver.rs`, `src/app/deliver/`). A loop (GravionLabs/skills `deliver-loop`) writes `.agents/deliver-loop/status.json` in its repository, atomically and against the schema `deliver-loop-status.schema.json` of GravionLabs/skills (`schemaVersion: 1`, raw URL `https://raw.githubusercontent.com/GravionLabs/skills/main/skills/delivery/deliver/schema/deliver-loop-status.schema.json`). poimen watches that file with `notify` for the git toplevel of every directory a pane is in (`deliver_watch`, events `deliver`; no polling and no GitHub call), so a change shows within a second. Read-only: poimen never writes the file.

Runs are grouped by subject (repository, subject kind and id; a run without a subject is a group of its own), because the deliver loop starts a new run after every stop. The view has three sections: **Running now** (groups with a running run that is not stale: the subject, its progress, the current task with its step, an `n/total` bar and the step text, the age of the last event and "Focus terminal", the run's `poimen.terminal` when it is open, else an agent pane inside the repository), **Needs you** (the needs-you attentions of all runs, each once, with its group and links; hidden when there are none) and **History** (the other groups by last update, collapsed). A group head shows the state of its newest run ("running, updated 2 min ago", "finished 12 min ago", "failed ...: text"); expanded it lists its runs as a timeline, newest first, one line each: start and end time, the outcome with its text (else its reason), the pull requests, and how many tasks were skipped, left open or wait for their merge, plus what `success` and `info` attentions said ("PR opened"). A line expands to the run's tasks (open while it runs, "left open" once it finished or was abandoned, "waiting for merge" with the pull request when the last step was `merge`; a task a later run took up shows only there), its warning, danger and needs-you attentions, the finished tasks per outcome, its links and its events. Colors follow the `tone` the writer set, never the outcome or the text: a failed run with tone `neutral` is not an error. Up/Down move over groups and lines, Enter expands, Escape collapses; expanded groups and lines are remembered. Runs come from the agent-events core (`.agents/events/<run>.jsonl` in the git directory of the repository, any writer; profiles are not needed and ignored); the legacy `.agents/deliver-loop/status.json` is still shown when a repository has no events. A run that is `running` but not updated for over an hour, and an abandoned run, is stale. Links open in the browser (GitHub links only); "Start loop" appears once per milestone group while none of its runs runs.

"Start loop" runs the task mode named `deliver-loop` (see `tasks`, a mode with `"worktree": false` and a `command` such as `["claude", "/deliver-loop", "{title}"]`) in a tab of the repository's space; `{nr}` is the milestone number (`M5` is 5), `{title}` its title and `{url}` its URL. Without such a mode the start fails with a notice naming the step.

The status bar shows `▶ M5 7/19` per running loop (`▶ 2 runs` for several; click opens the tab). A blocked item, a paused item, a needs-you item or a blocked result turns it into a warning (`⚠`). A status file with another `schemaVersion` shows a hint to update poimen instead of the run; an unreadable or invalid file shows its error. Only the pane directories are read from the server.

## Settings

Optional `~/.config/poimen/config.json`, watched and applied without a restart. Invalid entries log a warning and fall back to the default. It holds preferences only; UI state (sidebar width, open tabs) is kept by the app.

```json
{
  "theme": "system",
  "terminal": { "fontFamily": "JetBrains Mono", "fontSize": 13, "ghostty": false, "autoControl": true },
  "shortcuts": { "toggleSidebar": "Ctrl+Alt+B", "refresh": "" },
  "spaces": { "layout": { "panes": [{ "name": "editor", "command": "nvim" }, { "name": "shell", "split": { "from": "editor", "direction": "down", "ratio": 0.7 } }] } },
  "explorer": { "roots": ["~", "/srv/projects"], "showHidden": false },
  "sidebar": {
    "rows": {
      "agent": [["state_icon", { "token": "name", "bold": true }, "state_text"], ["agent", "$deliver_step", "branch", "dir"]]
    }
  }
}
```

- `theme`: `light`, `dark` or `system` (default). The toolbar button writes this entry; poimen writes only the entries its settings view and toggles change, never the rest of the file.
- `colorSchema`: the name of a bundled color scheme (the former value `"herdr"` is ignored with a log line), or a pair `{ "light": "<name>", "dark": "<name>" }` that `theme` picks from (`system` follows the OS appearance, light when it cannot be read) and that keeps the toolbar theme button working; a single scheme fixes light or dark from its background and disables that button (tooltip "Theme fixed by color schema <name>"), and a pair needs both names or it warns and uses `poimen`. Names: `poimen` (default, follows `theme`), or one of `catppuccin`, `tokyo-night`, `tokyo-night-day`, `dracula`, `gruvbox`, `gruvbox-light`, `one-dark`, `one-light`, `solarized`, `solarized-light`, `kanagawa`, `kanagawa-lotus`, `rose-pine`, `rose-pine-dawn`, `vesper`. The scheme colors the terminal and the chrome (surfaces, accent, status colors, derived from its palette) and decides light or dark from its background, so `theme` is ignored while one is set. A wrong type or an unknown name logs a warning and uses `poimen`. The values and licenses are in `src/app/themes/`.
- The settings view (the gear at the bottom of the activity bar, opens a Settings tab) has two panes like the JetBrains settings: a category tree on the left (*Appearance & Behavior*: Appearance with the color scheme below it, Notifications; *Workspace*: Explorer, Templates, Layouts, Trusted projects; *Backend*: Server, Agents) and the selected page on the right under a `Group › Page` breadcrumb. The search field above the tree (`Cmd+F` / `Ctrl+F` in the tab, Escape clears it) keeps the pages whose title or setting label matches, with their group, and highlights the matching setting on the page. The tree works with the arrow keys (Left/Right collapse and expand, Enter or Space opens a page); the selected page and the collapsed groups are UI state and survive a restart. Every control still saves immediately, without a Save button. It sets the appearance and the color scheme without editing the file: schemes are listed as dark and light with swatches, hovering or focusing one previews it live, a click or Enter saves it (leaving the list restores the saved one), and a single scheme or a light/dark pair can be chosen. Saving writes only `theme` or `colorSchema` in `config.json` and keeps your comments.
- Your own color schemes: drop WezTerm color scheme files (`.toml` with a `[colors]` table: `ansi` and `brights` of 8 colors each, `foreground`, `background`, optional `cursor_bg`, `selection_bg`, `selection_fg`, and an optional `[metadata] name`) into `~/.config/poimen/themes/` and use the name in `colorSchema`, alone or in a pair. The name is `metadata.name`, else the file name in kebab-case (`Tokyo Night.toml` is `tokyo-night`). Sources: the `colors/` directory of WezTerm or the `wezterm/` folder of [iTerm2-Color-Schemes](https://github.com/mbadolato/iTerm2-Color-Schemes) (MIT). The directory is watched and changes apply without a restart. A user scheme with a bundled name replaces the bundled one; an invalid file (or a repeated name) logs a warning naming the file and is skipped.
- `console`: keys of the `poimen` TUI (`poimen` without arguments: a sidebar with spaces, tabs and terminals, the selected terminal attached as controller; when another client controls it, the TUI observes and asks before it takes over). `console.prefix` (default `"C-b"`) is the key every TUI key follows; pressing it twice sends it to the terminal, every other key goes to the terminal unchanged. `console.keys` maps the actions after the prefix: `detach` (default `"d"`: leaves the TUI, the terminals keep running), `sidebar` (`"b"`: shows or hides it), `next` and `previous` (`"down"`, `"up"`: select and attach to the next or previous terminal). The TUI shows the tab bar of the focused space and the focused tab's split tree with borders; every change goes through the server (`tab.*` requests) and the view follows its events, so the app and the TUI show the same layout and focus. Every visible pane has its own attachment; only the focused pane controls. More actions after the prefix: `new_tab` (`"c"`), `next_tab`/`previous_tab` (`"n"`, `"p"`), `close_tab` (`"&"`), `split_right` (`"%"`), `split_down` (`"\""`), `close_pane` (`"x"`), `focus_left`/`focus_down`/`focus_up`/`focus_right` (`"h"`, `"j"`, `"k"`, `"l"`) and `resize_left`/`resize_down`/`resize_up`/`resize_right` (`"H"`, `"J"`, `"K"`, `"L"`: move the border of the focused pane by 5 %). `palette` (`":"`) opens the command palette: a filterable list to create (a directory input with Tab completion), rename and close spaces and terminals, open a tab, run the entries of the project file (`Project: <name>`, `Preset: <name>`, behind the same trust gate as the app) and start a task from an open issue (`Task: Start from issue`: issues through `gh`, task mode, then worktree and a space on it that runs the mode's command). A project file whose commands are not trusted yet is asked about in the palette (hash and commands: `t` trust, `w` without commands, Esc cancels) and the request is sent again with the answer. A click on a pane focuses it. Keys are written like `C-a`, `ctrl+a`, `M-x`, `q` or `pagedown`; an invalid key, an unknown action or two actions on one key warns and keeps the defaults. `poimen attach` uses `console.prefix` when it is a Ctrl+letter key. The TUI reads `sidebar.rows` like the app (`branch`, `dirty`, `sync` and `pr` stay empty there for now) and colors the terminal with a user scheme of `~/.config/poimen/themes/` named in `colorSchema`; with a bundled scheme it keeps the colors of the terminal it runs in. The mouse wheel scrolls the scrollback.
- `terminal.fontFamily` / `terminal.fontSize` (6 to 72, default 13).
- `backend` and `herdr` (removed with the herdr backend, #174): an old value in `config.json` is ignored and named once in a log line (`poimen: ignoring backend in config.json`), never an error. The app talks to `poimen-server` ([docs/protocol.md](docs/protocol.md)): spaces are server spaces, tabs and splits are kept by the server, and closing the app leaves the server and all terminals running. Live terminals carry raw PTY bytes: xterm.js tracks the mouse modes and keeps its own scrollback (`terminal.scrollback`); an observer renders at the size of the controller and is clipped. The agent of a terminal (`claude`, `copilot`) and its session come from the hooks, so icons, the Output panel and the Flow tab work. The status bar shows the server version.
- `terminal.scrollback` (default `10000`, 0 to 1000000): lines of scrollback xterm.js keeps.
- `terminal.autoControl`: `true` (default) opens panes for input when no other client controls them; `false` opens every tab read-only.
- `shortcuts`: accelerator per action (keys in the table above), such as `Cmd+Shift+K`, `CmdOrCtrl+Alt+Left` or `F5`. It needs Cmd, Ctrl or Alt (or is an F key); an empty string unbinds the action. Unknown actions, invalid accelerators and ones already used by another action log a warning and keep the default.
- `spaces.layout`: the pane layout of a **new** space (a focused existing space is not changed). It uses the schema of the herdr-plugins `layout-bootstrap`: `panes[]` with `name`, optional `command` (typed into the pane, then Enter) and, from the second pane on, `split.from` (an earlier pane, default the previous one), `split.direction` (`right` or `down`) and `split.ratio` (0 to 1, default 0.5, the share the split pane keeps); the first pane is the root pane of the space. Each pane starts in the space directory and is renamed to its `name`. The layout is chosen automatically: `layout` of `.poimen/config.json` at the repository root ([docs/project-config.md](docs/project-config.md)), else the deprecated `.agents/herdr-layout.json` (read until 1.0, with a warning), else `spaces.layout`, else the built-in default (`agent` left 60 % running `claude`, `tests` right top, `shell` right bottom). On the first start of a version with this seeding (a fresh install, or an update of an installation whose config has neither `spaces.layout` nor `spaceTemplates`), poimen writes `spaces.layout` into `config.json` once: an agent pane per installed agent (`claude`, then `copilot`, found on the login-shell `PATH`) and always a `shell` pane, the first agent as the root pane, `copilot` split right of it and `shell` below it. A config with either key is never changed, and the seeding does not run again, so a deleted default stays deleted. For existing installations this replaces the built-in default layout for new spaces. An invalid project file shows a warning in the status bar naming the file and the problem, and the space gets a single pane; an invalid `spaces.layout` logs a warning and uses the default. The **Layouts** page of the settings view lists the named layouts and shows `spaces.layout` (or the built-in default) as the layout `default`, the one new spaces get unless a template names another; editing it there writes a named layout `default` to `layouts[]`, after which `spaces.layout` is ignored (and still works while `layouts[]` has no `default`).
- `spaceTemplates`: directory-matched templates for a **new** space, an array of `{ "name", "match": { "dir"?, "remote"? }, "agent", "model"?, "layout"? }`. `name` is required and unique; `match.dir` is an absolute directory or starts with `~`; `match.remote` is `{ "provider": "github", "owner" }` or `{ "provider": "azure-devops", "organization", "project" }` and is compared with the `origin` of the repository (GitHub HTTPS/SSH, `dev.azure.com`, `<org>.visualstudio.com`, `ssh.dev.azure.com`; URL-encoded names are decoded; owner, organization and project compare case-insensitively); with both `dir` and `remote` set both must match, and a template without `match` (or with `match: {}`) is the **default template**: it applies to any directory no other template matches (at most one, a second is ignored with a warning). On the first start (the same condition as for `spaces.layout`) poimen writes one default template named `default`, with the first installed agent (`claude`, else `copilot`, else the first harness) and no `layout` of its own, so it uses `spaces.layout`; it is listed as "Default" on the Spaces page, which edits it or adds it again, and it is never written back once deleted; `agent` is a harness id from `harnesses`; `model` is optional; `layout` uses the schema of `spaces.layout`. One template applies: a match on both `dir` and `remote` beats `remote` only, which beats `dir` only; a match on `dir` only beats the default; among equals the longest `match.dir` (path-segment prefix: `~/src/a` does not match `~/src/ab`; case-insensitive on Windows and macOS) wins. A directory without a repository or without `origin` matches by `dir` only. Layout order: project `layout`, then the template `layout`, then `spaces.layout`, then the built-in default. The template's agent (and model) is typed into the root pane of the layout when that pane has no command of its own (the built-in default's `claude` counts as none); a task's command still wins. An unknown harness or one whose program is not on the `PATH` creates the space without the agent and shows a warning naming the template. Invalid entries warn and are skipped. Templates are user config and need no trust. The **Spaces** page of the settings view edits them without touching the file by hand: it lists name, match and agent, and a form edits one template (name, directory with a folder picker, remote, agent from the configured harnesses with unavailable ones marked, model from the harness's `models`, and a layout that starts from none, the built-in default, `spaces.layout` or a project preset, with the panes editable as name and command). The form checks what the backend checks (unique name, a known harness, a valid layout), the backend's `spaceTemplates` warnings show on the page, and a save writes only `spaceTemplates`. The new-space dialog shows `Template: <name> · <agent>` for the typed directory, `Template: <name> (default) · <agent>` for the default template, or `No template`. Changed default for existing installations: a config with neither `spaces.layout` nor `spaceTemplates` gets both on the first start of this version; new spaces then use the seeded layout and the default template's agent instead of the built-in layout and no agent.
- `layouts` (#609, [ADR 0011](docs/adr/0011-named-layouts-referenced-by-templates.md)): named layouts, an array of `{ "name", "tabs" }`. `name` is required and unique; a tab is flat (`name?`, `command?`, `cwd?`) or has splits (`name?`, `root`: a leaf `{ "kind": "terminal", "name"?, "command"?, "cwd"? }` or `{ "kind": "split", "direction": "right"|"down", "ratio"?, "children": [node, node] }`), never both; `children[]` are nested tabs and `place` (`direction`, `of?`, `ratio?`) is read by the app only (an unknown `of` or a cycle warns and is ignored). `panes[]` is accepted in place of `tabs[]` and converted on read. A template's `layout` may be a name from `layouts` (an unknown name warns and falls through to the layout `default`) or, as before, an inline layout. `spaces.layout` is read as the layout `default` unless `layouts` has one (then `spaces.layout` is ignored with a warning); nothing is migrated and `config.json` is not rewritten. Invalid entries warn and are skipped. The resolver is `poimen_core::layout::resolve` and `space_layout::inputs`; the server builds every tab (children after their parent) and the app's rebuild reads the same layout.
- The **Layouts** page of the settings view (#610) edits `layouts[]`: list, new, duplicate, rename and delete (refused, naming the templates, while a template refers to the layout, and refused again by the backend when the config changed meanwhile); the editor takes tabs with nested child tabs (add, move, indent, outdent, delete with its children), per tab one terminal (`command`, `cwd`) or a split tree, and a `place` (`direction`, `of` from the other tabs, `ratio`), with a preview of the spaces tree and of the editor groups. The **Templates** page (the former Spaces page) picks a layout by name. "Save current tab as layout…" in a tab's menu stores the server's tab, its split tree and its child tabs as a new named layout (the server keeps no `place`, so none is written: set it on the Layouts page). Saves write only `layouts` (comments kept) and a write that changes nothing leaves the file untouched.
- `machines`: remote machines (ADR 0008), an array of `{ "name", "ssh", "reposDir"?, "serverPath"? }`. `name` is required and unique; `ssh` is the target as in `~/.ssh/config` (a `Host` alias or `user@host`, one word, not an option); `reposDir` is where repositories live on the machine, with `{owner}` and `{repo}` (default `~/Source/{owner}/{repo}`). Invalid entries warn and are skipped; the rest loads. poimen keeps one connection per machine with `ssh -T -o BatchMode=yes <target> poimen-server stdio` (keys and hosts from your ssh setup; poimen never prompts for, stores or logs a password or a key) and reports `connecting`, `connected`, `offline` (with the ssh error) or `incompatible` (other protocol, with both versions; no further requests). A dropped connection is tried again after 1 s, doubling up to 60 s, or at once on demand; the terminals on the machine keep running while it is disconnected. `serverPath` is set by poimen when it installed the server where a non-interactive ssh `PATH` does not find it (`$HOME/.local/bin/poimen-server`); the connection then calls that path. A machine without the server (or with an incompatible one, Linux x86_64 or aarch64) offers "Install server…" / "Update server…" on the Machines page (ADR 0013): after a confirmation that shows the exact commands, poimen downloads the archive of its own version here, checks it against `SHA256SUMS`, streams it over ssh into `~/.local/bin` (verified with `--version` before it is moved into place) and reconnects; no process on the machine is stopped, no sudo, no profile is edited, no secret leaves this Mac. You can still install by hand (see `poimen-server stdio` in [docs/protocol.md](docs/protocol.md)).
- `trustedProjects`: repository root to the SHA-256 of the project file (`.poimen/config.json`, else the deprecated `.agents/herdr-layout.json`) you trusted. The commands of a project file (layout panes, setup, teardown, commands, presets) run only while its hash matches; otherwise a dialog lists every command and offers "Trust and run", "Run without project commands" (panes are built but nothing is typed) and "Cancel". A changed file revokes the trust. The **Trusted projects** section of the settings view lists the roots with a "Revoke" button; `spaces.layout` needs no trust. See [docs/project-config.md](docs/project-config.md#trust).
- `tasks`: how an issue becomes work (the modes are read by the task start; there is no settings view yet). `modes[]` with `name` (unique), optional `worktree` (default `true`), `branch` (template, default `{type}/{nr}-{slug}`) and `cleanup`; `worktreeDir` (template relative to the repository root, default `../{repo}-{nr}`). A mode starts an agent or runs a command. Agent mode: `harness` (an id of `harnesses`, default the first one, `claude`), optional `model` and `prompt` (template, default `Work on GitHub issue #{nr}: {title} ({url})`); the argv comes from the harness (see `harnesses`). Command mode: `command` as an argv array, e.g. `["pwsh", "Invoke-DeliverLoop.ps1", "-Target", "{nr}"]`; `command` excludes `harness`, `model` and `prompt`. `cleanup` is an argv array too. Placeholders expand per array element and no shell is involved, so a title with quotes, `$()`, `;` or spaces stays one argument. Without `modes` there is one mode `agent`: worktree, the default harness and prompt. Placeholders: `{nr}`, `{title}`, `{url}`, `{repo}`, `{slug}` (title without `[Level]`, type and scope, lowercase, `-` for other characters, at most 40), `{type}` (`feat`, `fix`, `refactor`, `docs`, `build`, `chore`, `test`, `perf`, `ci`, else `issue`), and in `command`, `cleanup` and `prompt` also `{branch}`; in `command` and `cleanup` also `{prompt}` (the default prompt), in `cleanup` also `{pr}` (the merged pull request). Deprecated, accepted for one release with a warning (`tasks.modes.<name>: string command is deprecated, use harness + prompt or an argv list`): `command` and `cleanup` as a shell string, whose values are single-quoted. An invalid entry (unknown placeholder, `command` with `harness`, malformed `command`, duplicate `name`) logs a warning and is skipped.
- `harnesses`: the agent CLIs poimen can start, as a map from id to `command` (argv array), `modelArgs` (argv template with `{model}`, appended only when a model is chosen), `promptArgs` (argv template with `{prompt}`), `models[]`, an optional `defaultModel`, an optional `exitInput` (text typed at the agent's prompt to end its session) and `resumeArgs` (argv template with `{session}`, appended to `command` to resume a session; none means the harness cannot resume). Templates expand per argv element and never go through a shell, so a prompt with spaces, quotes or newlines stays one argument. Defaults: `claude` (`--model {model}`, prompt as the argument; models `opus`, `sonnet`, `haiku`) and `copilot` (`--model {model}`, `-i {prompt}`; models `auto`, `gpt-5.4`); both default to `exitInput` `/exit` and `resumeArgs` `["--resume", "{session}"]`. The Settings view lists them under "Agents" with availability (read-only; edit `config.json`). An invalid entry becomes a settings warning and is skipped.
- `agents.silentAfter` (#898): minutes (default `10`, `0` is off) an agent may stay `working` without any report from its hooks before the server marks it silent (`silent_since` of the terminal's `agent`, event `agent.status_changed`). The time counts from the last hook report (every tool call reports), not from terminal output, because a spinner keeps writing while a call hangs. The next report clears the mark. The app shows `silent 12m` on the sidebar row and the tab (warning color, remote panes too) and adds one notification center entry per transition (#899); no ring, sound or badge. The server reads the setting again at most every 30 s. Invalid values log a warning and keep `10`.
- `agents.claude.classicRenderer`: `true` makes Claude Code use its classic renderer in poimen terminals (default `false`). Every terminal poimen creates while it is on gets `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1`, so `claude` writes to the normal screen and xterm.js keeps scrollback, scrollbar, selection and search. Running terminals keep their environment; the change applies to terminals created afterwards. The alternative is `/tui default` inside Claude Code. Trade-off: the classic renderer may flicker on long output, and Claude's `/focus` view needs the full-screen renderer. The toggle is under Settings > Agents and needs the poimen backend (disabled with herdr). Invalid values log a warning and keep `false`.
- `agents.keepAwake` (#987): `true` makes poimen-server hold a sleep inhibitor while a local agent is `working` (not silent) or a run is running (default `false`; switch in Settings, Agents). `caffeinate` on macOS, `systemd-inhibit` on Linux, the execution state through PowerShell on Windows. It is released a minute after the last one stopped, when the setting goes off, and when the server ends; the server holds it, so it works with the app closed. The status bar shows `awake` while it is held.
- `agents.hibernateAfter` (#903, [ADR 0014](docs/adr/0014-hibernate-idle-agents.md)): minutes after which poimen-server hibernates an agent that has been `done` without change (default absent or `0`: off). The server types the harness's `exitInput` (`/exit` for the built-in `claude` and `copilot`) into the terminal and remembers the agent and its session id; the terminal and its shell stay. It only applies to a hook-reported agent whose harness has `exitInput` and `resumeArgs`, with a known session id, and never while the agent works or is blocked or a client controls the terminal. Any later agent report ends the hibernation state. The first controller attach (#904: the app, `poimen attach --control`, selecting the terminal in the TUI) resumes the session: once the shell is at its prompt the server types the harness's command with `resumeArgs`; an observer attach does nothing, and one resume happens per hibernation. A resume whose agent does not report within 30 s ends the hibernation, leaves the shell at its prompt and raises one notification. Rows show `hibernated` and do not count as waiting or unread. A running server reads the setting on its next pass (every 5 s).
- System notifications: poimen sends none (#676; on macOS waiting notifications froze the window after a few hours). A leftover `notifications` key is ignored.
- `sounds` (#724): `{ "blocked": false, "done": false }`, each `false` (default), `true` (a built-in tone made with Web Audio, no asset: falling pair for blocked, rising pair for done) or the path of an audio file (`~/` is your home; a regular file up to 1 MiB, read by the app from this setting only; unreadable, too large or undecodable logs a warning and plays the built-in tone). It plays when an agent turns blocked or done while its tab is not viewed, remote agents included (nothing for a machine that is not connected); the first snapshot of a backend session is silent, transitions within 2 s play one sound, and blocked wins over done. The Appearance page of the settings has a "Sounds" section with a switch, a file field and "Test" for each. Blocked and done agents show as marks on tabs and sidebar rows and in the notification center view.
- `usage` (#784): `{ "claude": true }`. The status bar shows how close you are to the Claude limits: the tightest window (`5h 62 %`, warning color from 80 %) with all windows (5 hours, 7 days, Opus, Sonnet) and their reset times in the tooltip. poimen reads your Claude Code login (`<CLAUDE_CONFIG_DIR or ~/.claude>/.credentials.json`, else on macOS the Keychain item `Claude Code-credentials`) and asks `https://api.anthropic.com/api/oauth/usage`, the endpoint the Claude CLI uses, at start, every 5 minutes and when the window gets focus (at most once a minute, only while the app runs); the token is sent to that endpoint only and never stored or logged. The endpoint is not a documented public API: without a login, on an HTTP error or an unknown answer the item is hidden and one warning names the cause. `false` reads no token and sends no request.
  - **Dock badge:** the dock icon shows how many agents wait for you (blocked) and clears at 0; it follows the agent status events of the backend. Platforms without dock badges ignore it (a console warning).
- `explorer.roots`: the roots of the Explorer view (second item of the activity bar), a non-empty list of absolute paths; a leading `~` is the home directory (default `["~"]`). The tree shows directories only, sorted by name, and lists a folder when it expands; an unreadable folder shows no children. `explorer.showHidden` (default `false`) shows directories that start with a dot. The active view and the expanded folders are UI state and survive a restart. Double-clicking a folder, or "Create space here" in its context menu, creates a space for it (with the configured layout) or focuses the existing one; folders that are the working directory of a pane of a space carry a dot. The filter field in the head ("Filter folders"; `Cmd+F` / `Ctrl+F` in the explorer focuses it, Escape clears it) keeps the folders whose name contains the text (case-insensitive, match highlighted) together with their ancestors, which show expanded; it only looks at folders that are already loaded (roots and expanded folders) and never changes the remembered expanded folders. A wrong type logs a warning and keeps the default. The **Explorer** section of the settings view manages the roots without editing the file: "Add folder…" (native folder picker), remove (not the last one), move up/down, and "Show hidden folders"; it writes only `explorer.roots` / `explorer.showHidden` (paths under the home directory as `~/…`) and keeps your comments.
- `sidebar.layout`: `"tree"` (default) shows workspaces with their panes below; `"split"` shows two lists: **Spaces** (the workspaces, the selected one lists its terminal panes) and **Agents** (every agent pane across the workspaces, with its workspace name, rendered with `sidebar.rows.agent`), stacked with a divider line between them: drag the divider (or focus it and use the arrow keys, Shift for bigger steps) to resize the two lists, each keeps at least 15 % and scrolls on its own, and the ratio survives a restart (UI state, default 50/50). The toggle button next to the title "Spaces" switches it and writes this entry; the selected workspace of `split` is UI state, not a setting. `"cards"` shows one card per local space: a header with the status dot, the first line of `sidebar.rows.space`, the unread count and the actions new terminal, configure and close (more in a `⋯` menu with the entries of the context menu), the further lines of `sidebar.rows.space` below it, and a body with the tabs and terminals as rows of `sidebar.rows`; the header collapses the card, and the collapsed state per space is UI state. The toggle cycles `tree`, `split`, `cards`. The console TUI ignores `cards`. Anything else logs a warning and uses `tree`.
- `sidebar.sort`: `"manual"` (default) keeps the order you arranged by drag and drop (UI state); `"name"` lists the spaces alphabetically (numbers in numeric order, so `#9` comes before `#12`; ties by creation number), also the spaces of remote machines. `"attention"` puts the spaces that need you first, ranked by their most urgent agent (blocked, then done and unread, then working, then idle or done and read, then no agent; by name inside a rank); a re-sort caused by a status change waits until no status changed for 3 seconds, so rows do not jump while you aim at one. `"recent"` lists the spaces you focused last first (the time a pane or the overview of a space became the active tab; spaces never focused follow, newest first). On the spaces of remote machines `attention` applies and `recent` sorts by name. In every mode except `manual` drag and drop of spaces and "Move Space Up/Down" are off. The sort button in the Spaces header and the palette commands "Sort Spaces: Manual", "Sort Spaces: By Name", "By Attention" and "Most Recent" write this entry; "Sort alphabetically now" stores the alphabetical order as your manual order once and switches back to `manual`. The TUI (`poimen`) follows `sidebar.sort` too: `name` lists its spaces in the same alphabetical order, `attention` ranks them by the hook-reported agent status (done counts as unread through the TUI's own notification marks), `recent` falls back to `name` (the focus times are UI state of the app), `manual` keeps the server order (the manual order is UI state of the app). Anything else logs a warning and uses `manual`.
- `sidebar.agents`: `"list"` (default) keeps the Agents section of the split layout in space order; `"priority"` groups the agents into the sections "Needs you" (blocked), "Done" (done and unread), "Working" and "Idle" (idle, done and read, unknown), each foldable with its count (the fold state is UI state). Inside a section the agent whose status changed first comes first, ties by name. The status is the effective one, remote agents are included. Every agent row shows the time since its last status change (`5m`, `2h`, `3d`), refreshed once a minute, in both modes; a pane first seen at app start counts from that snapshot. A re-sort caused by a status change waits like `sidebar.sort: attention` (3 seconds without a change). In the split layout with `priority`, "Next Waiting Agent" visits the blocked agents in the order shown. The toggle in the header of the Agents section and the palette commands "Agents: By Priority" and "Agents: In Space Order" write this entry. Anything else logs a warning and uses `list`.
- `sidebar.groupWorktrees`: `true` (default) lists the spaces whose directory is a linked git worktree directly below the space of the main checkout of the same repository, indented, with the `wt ` prefix of the branch left out; heads and worktrees each follow the sort mode, and in `manual` mode dragging a head moves its worktrees along while a worktree can only be reordered among its siblings. A repository without a space for its main checkout, a space outside a repository and the spaces of remote machines stay in the flat list. The filter shows the main space of a matching worktree. `false` keeps the flat list. Anything else logs a warning and uses `true`.
- `sidebar.showBaseBranch`: `false` (default) leaves the `branch` token of a space row empty while the space is on the base branch of its repository (`origin/release/next` when it exists, else the default branch of `origin`; detached HEADs and worktrees are always shown); `true` shows it everywhere. `dirty`, `sync` and `pr` are unaffected. A value that is not a boolean logs a warning and uses `false`.
- `sidebar.rows.workspace` / `sidebar.rows.agent` / `sidebar.rows.terminal`: what a row of the Spaces tree shows, a list of lines, each a list of tokens (a name, or `{ "token": "<name>", "bold": true, "dim": true }`). Tokens: `state_icon` (status dot), `name`, `state_text`, `agent`, `title` (the `deliver_step` token, else the terminal title), `branch`, `dirty` (`●3`: changed plus untracked files, empty when clean), `sync` (`↑2 ↓1` against the upstream, empty when even or without one), `pr` (the open or merged pull request of the branch: `#123` plus ✓ passed, ✗ failed or … pending checks, `merged` for a merged one, dimmed for a draft; tooltip with title and check counts; a click opens it in the browser; read through `gh` with the 30 s cache, empty without `gh`, a login or a GitHub `origin`, and for `main`, `master`, `release/*` and detached HEADs; not in the default layout), `notification` (latest notification text of the agent, e.g. the permission question, from the Claude Code and Copilot CLI hooks; one line with an ellipsis, the full text in the tooltip; on a workspace row the newest of its agents; cleared when the agent works again; empty on the herdr backend; not in the default layout), `dir` (short path), `tab`, and `$<name>` (the herdr token `<name>` of the pane). On a workspace row `branch`, `dirty`, `sync` and `dir` are the values all its panes share; on a pane row they show only when they differ from the workspace. Empty values and values equal to an earlier one on the row are skipped. The filter matches the shown values. The default is `workspace`: `[["state_icon","name","state_text","branch","dirty","sync","dir"]]`, `agent` and `terminal`: `[["state_icon","name","state_text"],["agent","title","branch","dir"]]`. An unknown token, a wrong type or an empty list logs a warning and keeps the default of that row type.
- Export and import (#581): Settings › General › **Export & import**. "Export settings…" writes `config.json` as a JSON file through a save dialog, without `trustedProjects` (trust is per machine). "Import settings…" reads a JSON file (up to 1 MiB, comments allowed), checks each entry with the settings loader and shows what it would add, change and remove (dotted keys, templates by name) before anything is written; invalid entries are listed and never written, `trustedProjects` in the file is left out. *Merge* (default) keeps the keys the file does not set (objects merge key by key, space templates by name); *Replace* removes them, except `trustedProjects`. Import writes only the keys of that diff, so comments elsewhere stay. On the **Spaces** page each template has "Export…" (the template with its layout as `{ "spaceTemplates": [...] }`) and "Import template…" merges the templates of a file by name. UI state is never part of it.
- `terminal.ghostty`: `true` takes font family, size, `background`, `foreground`, `cursor-color`, `selection-background`, `selection-foreground` and `palette = N=#rrggbb` (0 to 15) from `~/.config/ghostty/config`. The colors lie over the terminal colors of the color scheme (the chrome stays from the scheme); explicit entries above win. A Ghostty `theme = <name>` is not read.

## Console

The `poimen` binary (CLI and TUI, [ADR 0006](docs/adr/0006-poimen-console-with-herdr-scope.md)) talks to `poimen-server`. It ships with every installer and as its own download:

- **macOS:** inside the app at `/Applications/poimen.app/Contents/MacOS/poimen`. Link it onto the PATH with `sudo ln -sf /Applications/poimen.app/Contents/MacOS/poimen /usr/local/bin/poimen`.
- **Windows:** the `-setup.exe` and the `.msi` install `poimen.exe` next to the app and add that directory to your user PATH (open a new terminal after the install).
- **Linux:** the `.deb` and `.rpm` of the app install `/usr/bin/poimen`. For a host without the app, install the `poimen-cli` package (`.deb` or `.rpm` of the release; it conflicts with the app package). In the AppImage the binary is at `squashfs-root/usr/bin/poimen` after `./poimen_<version>_amd64.AppImage --appimage-extract`.
- **Without the app:** the release assets `poimen-<version>-<target>.tar.gz` (Linux musl, macOS) and `.zip` (Windows) hold only the binary.

**`poimen doctor`** checks the setup, one line per check (`ok`, `warning` or `error`): the console, the server (answers, version, protocol, outdated or incompatible), the `poimen-pty-host` next to it, `server.json` (parses, counts, an interrupted save or a damaged copy beside it), the agent CLIs `claude`, `copilot` and `gemini` on the login-shell `PATH` with their hooks and MCP entry, and `gh` and `git`. `--json` prints the same as one JSON document (`checks[]` with `id`, `status`, `detail`). `--bundle <file>` also writes a local JSON file for a bug report: the report, the shape of `server.json` (ids and counts; no names, directories, commands or agent messages) and the last 200 KiB of `server.log`, `hooks.log` and the host logs. The file is private (0600), never overwrites an existing one and is not uploaded; read it before you send it. It works without a running server. Exit code 0 when no check is an error, 1 otherwise, 2 for a usage error. It fixes nothing: hooks are installed with `poimen-server integration install <agent>`.

A pre-release (RC) installs the CLI as `poimen-cli-rc` beside the "Poimen RC" app and has no `.rpm`.

## Releases

- Work branches are cut from `release/next` and merge into it; the `Release branch` workflow keeps the release PR `release/next` → `main` open and current (`github-release` skill).
- Work PRs into `release/**` are **squash** merged; their PR title must be a Conventional Commit (`pr-checks` title job) and becomes the one commit of the change. The `release` ruleset also allows `merge`, but only for the back-merge of `main` into `release/next` after a release (a squash drops the ancestry, `github-release` skill); never merge a work PR that way.
- A release is made by merging that release PR into `main` with a **merge commit, never squash** (the `main` ruleset allows only merge commits), so GitVersion sees every commit. A hotfix PR into `main` is merged the same way, and every commit of it must be a Conventional Commit.
- The version comes from Conventional Commits (`versioning/determine-version` of GravionLabs/ci, `GitVersion.yml`): `fix:`/`perf:`/`revert:` → patch, `feat:` → minor, `type!:` or `BREAKING CHANGE:` → major. A release with only fixes is a patch, one with a `feat:` a minor.
- While the version is 0.x, use **no** `!` and no `BREAKING CHANGE:` until 1.0 is intended: either one jumps the version to 1.0.0.
- On the push to `main`, `.github/workflows/release.yml` runs the CI checks, determines the version, commits `CHANGELOG.md` (git-cliff, `cliff.toml`) to `main`, tags `v<version>`, creates the GitHub Release and closes the issues the release delivered. The changelog commit is pushed with the `GH_PAT` secret (a repository admin, bypass actor of the `main` ruleset).
- `release.yml` writes the released version into `package.json`, `src-tauri/Cargo.toml`, `Cargo.lock` and `src-tauri/tauri.conf.json` and commits it (`chore(release): set version <v> [skip ci]`) before the changelog commit, so the tag points at manifests carrying the released version. Between releases they hold the previous release's version.
- The status bar shows `frontend poimen <version>` (the Tauri app version from `tauri.conf.json`) and `backend poimen <version>` (poimen-server; `backend poimen ?` when unreachable or too old; warning colour and tooltip when the protocol differs from the supported one). The `tauri.conf.json` version, set by `release.yml`, is the source of truth. The app and the `poimen-*` crates inherit one workspace version, so both labels agree after a release (`src-tauri/tests/versions.rs` guards it). Local builds show the last released version.
- The same run builds the installers after the release is created and attaches them to the GitHub release `v<version>`: Linux x64 (`.deb`, `.rpm`, `.AppImage`), macOS arm64 (`.dmg`; no Intel build) and Windows x64 (`.msi`, `.exe`). Their names and the status bar carry the released version. The macOS app is signed and notarized when the Apple secrets exist ([#45](https://github.com/GravionLabs/poimen/issues/45), [docs/releasing.md](docs/releasing.md)); Windows installers are **not code-signed** yet and SmartScreen warns on first start. The `checksums` job then attaches `SHA256SUMS` over the installers and update archives and attests them with `actions/attest-build-provenance` (`scripts/release-checksums.sh`, #522); users verify a download with `gh attestation verify <file> --repo GravionLabs/poimen` (installation guide, "Verify the download"). They come from the `GravionLabs/ci/tauri/installers@v1` action (the building block of `tauri-app.yml`; the workflow itself assumes a root Cargo workspace and does its own versioning and release). A manual `workflow_dispatch` run of `release.yml` on a branch builds the same matrix as a `-beta<nnn>` version (see below) and uploads it as workflow artifacts, with no tag, release or commit; pull requests never build installers.
- **Pre-release (RC).** Run `release.yml` with `workflow_dispatch` on `release/next`; the channel comes from the branch (`determine-version` of GravionLabs/ci, no input). It gives `<next stable>-rc<nnn>` (`nnn` = commits since the last stable tag, zero-padded to three digits, so each commit has its own number), the run tags `v<version>` on `release/next`, creates a GitHub **pre-release** and attaches the installers: Linux `.deb`, `.AppImage`, macOS `.dmg`, Windows `-setup.exe`; no `.msi` (WiX needs a numeric version) and no `.rpm` (an RPM version allows no `-`). It commits nothing to `main` or `release/next`, does not touch `CHANGELOG.md` and closes no issues. GitVersion (`tag-prefix` in `GitVersion.yml`) and git-cliff (`tag_pattern` in `cliff.toml`) ignore `-rc` tags, so the next stable version and its changelog are the same with and without pre-releases. On any other branch the same dispatch gives `<next stable>-beta<nnn>` and uploads the Linux `.deb` and `.AppImage`, macOS `.dmg` and Windows `-setup.exe` as workflow artifacts (7 days); no tag, release or commit. Both are built for the channel `rc` (`POIMEN_CHANNEL=rc`, overlay `src-tauri/tauri.rc.conf.json`) and install as **Poimen RC** next to the stable app, with their own server (`poimen-server-rc`), settings (`~/.config/poimen-rc/`) and hooks; they never update themselves, and stable installs never get a pre-release as an update, see [docs/updater.md](docs/updater.md).
- **Release flow:** release review of `release/next` -> pre-release (RC, above) -> release PR open at once -> manual RC test beside it ([`docs/manual-acceptance.md`](docs/manual-acceptance.md), #432; the RC test is no gate) -> bugs in the milestone while the release PR is open become a new RC, otherwise they go to the next milestone -> human merge of the release PR (the stable release).
- The installers also carry signed update packages and `latest.json` (secrets `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, `src-tauri/tauri.bundle.conf.json`); the status bar offers **Check for updates**, see [docs/updater.md](docs/updater.md).
- Tags are `v<major>.<minor>.<patch>`, as in the other GravionLabs repositories; milestones are named `M<n>` while open and get the version when the release is tagged (`M<n> (x.y.z)`); the milestones up to `v0.7.1` were renumbered in release order (`M1 (0.2.0)` to `M7 (0.7.1)`).
- The public site (`site/`, VitePress, published to GitHub Pages by `.github/workflows/pages.yml`) is described in "Site" below.
- The rulesets `main` and `release` are created by `scripts/setup-rulesets.sh`.
