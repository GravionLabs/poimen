# poimen-server protocol

Protocol version: **4** (version 1 had no terminal output; version 2 adds `terminal.attach`, the stream records and the controller rules for `terminal.input` and `terminal.resize`; version 3 adds tokens per terminal: `terminal.report_tokens`, `terminal.clear_tokens`, `tokens` of Terminal and the `terminal.tokens_changed` event; version 4 adds tabs and split trees per space: `tabs` and `active_tab` of Space, Tab and its nodes, the `tab.*` requests, the `tab.*` and `space.changed` events, see Tabs and splits).

`poimen-server` is a headless daemon that owns the PTYs, so shells and agents keep running when the app closes. The protocol is client-neutral: no Tauri or app concept appears in it. The wire types live in `src-tauri/crates/poimen-protocol`, a client in `src-tauri/crates/poimen-client`.

## Transport

- NDJSON over a local socket (`interprocess::local_socket`, in `poimen_client::transport`): one JSON object per line, UTF-8, `\n` terminated. On Linux and macOS it is a Unix domain socket at the socket path; on Windows it is the named pipe `\\.\pipe\<socket path>`, and the socket path holds a marker file (`<pid>:<unix nanos>`) so "is a server running?" works the same on both. The pipe's DACL (`D:P(A;;GA;;;SY)(A;;GA;;;OW)`) admits SYSTEM and the owner only, and its buffers are 64 KiB.
- Socket path: `$POIMEN_SOCKET`, else `$XDG_RUNTIME_DIR/poimen/server.sock`, else `<temp dir>/poimen-<user>/server.sock`. Windows: `$POIMEN_SOCKET`, else `%LOCALAPPDATA%\poimen-server\server.sock`, else `<temp dir>\poimen-%USERNAME%\server.sock`. Unix: the directory has mode 0700, the socket 0600. One server per user (it holds `server.lock` next to the socket): a second server on a live socket exits; a stale socket file (Windows: a marker without a pipe) is replaced; anything else at the path is left alone and the server refuses to start.
- Channels: a binary is built for the channel `stable` or `rc` (`POIMEN_CHANNEL` at build time, `poimen_protocol::CHANNEL`; an unknown value fails the build). On `rc` every directory above is named with `-rc` (`$XDG_RUNTIME_DIR/poimen-rc/server.sock`, `<temp dir>/poimen-rc-<user>/server.sock`, `%LOCALAPPDATA%\poimen-server-rc\server.sock`), so a stable and an rc server run side by side, one per user and channel. The app and the server ignore a `$POIMEN_SOCKET` that is the default socket of the other channel (they were started from a terminal of the other installation) and use their own; `poimen-server report` uses `$POIMEN_SOCKET` as it is, the server of the terminal it runs in.
- Named pipes have no I/O timeouts and no `shutdown`. On Windows a client bounds a request by waiting on a helper thread, and the server's write timeout for a client that stops reading (5 s) applies on Unix only.
- Requests use short-lived connections (connect, one or more requests, close). A connection that sent `events.subscribe` only receives events afterwards.
- A line that is not a request gets an error response and the connection stays open.

## Messages

Request: `{"id": "1", "method": "space.create", "params": {...}}`. `id` is any string chosen by the client; `params` may be omitted when a method has no required parameter.

Response: `{"id": "1", "result": {...}}` or `{"id": "1", "error": {"code": "not_found", "message": "..."}}`. `id` is `null` in an error for a line that could not be parsed.

Event: `{"event": "terminal.exited", "data": {...}}`. Lines with an `event` field are events; all others are responses.

Error codes: `parse_error`, `invalid_request`, `unknown_method`, `invalid_params`, `not_found`, `exited` (the terminal's process has exited), `spawn_failed`, `not_controller`, `conflict`, `internal`.

## Objects

Space: `{"id": "s1", "name": "api", "cwd": "/home/me/api", "tabs": ["tab2", "tab5"], "active_tab": "tab5"}` (`tabs` in order; `active_tab` absent while the space has no tab; both absent from a protocol 3 server).

Tab: `{"tab_id": "tab2", "space_id": "s1", "name": "zsh", "root": Node, "active_terminal": "t3"}`. `active_terminal` is the focused leaf of the tab.

Node: `{"kind": "terminal", "terminal_id": "t3"}` or `{"kind": "split", "split_id": "split7", "direction": "right" | "down", "ratio": 0.5, "children": [Node, Node]}`. `right` puts the second child right of the first, `down` below it; `ratio` is the share of the first child, above 0 and below 1. `split_id` is assigned by the server, unique within it and stable for the life of the split; it is persisted with the tree and never given to another node, also across restarts.

Terminal: `{"id": "t2", "space_id": "s1", "name": "zsh", "cwd": "...", "cols": 80, "rows": 24, "status": "running" | "exited", "exit_code": 0, "program": "/bin/zsh"}` (`exit_code` only when exited; `program` is the program the terminal runs, absent from older servers) `agent` (`{"status": "idle" | "working" | "blocked" | "done", "agent": "claude", "session_id": "..."}`; `agent` and `session_id` optional) is present while hooks report an agent in the terminal, and cleared when it ends or the process exits.

The server owns the tabs and the split tree of each space, so every client shows the same layout (ADR 0006); editor groups and app-only tabs stay the client's business. Terminal ids are unique per server run; ids of spaces, tabs and splits survive restarts.

## Tabs and splits

Every space has its tabs in order (`Space.tabs`), each with a split tree of terminals. The tree and the terminal set never disagree: every leaf is a running terminal and every running terminal is in exactly one leaf. A change of the layout and its events are made under the same lock as the terminal change that caused it, so a subscriber sees `terminal.created` before the tab that holds it, and `terminal.closed` or `terminal.exited` before the tab without it.

- `terminal.create` gives the terminal a tab of its own, so clients that know nothing of tabs keep working. A new tab goes last and becomes `active_tab` only when the space had none.
- Closing or the exit of a terminal removes its leaf: the leaf's sibling takes the parent's place (the split goes with its `split_id`). When the leaf was the tab's `active_terminal`, the first leaf of the node that took the place becomes active. The last terminal of a tab closes the tab; when it was the `active_tab`, the tab that took its place (else the one before it) becomes active.
- Splits are addressed by `split_id`, never by a path in the tree: clients change the same tree at the same time, and a path shifts when another client splits or closes a pane.
- Focus is shared: `active_tab` and `active_terminal` change only through `tab.focus` (or when the focused tab or leaf goes away), and the last client that sends `tab.focus` wins. A client that only views a tab does not send it.

Events: `tab.created {tab}`, `tab.changed {tab}` (the full tab after any change of its tree, name, place in the order or focus) and `tab.closed {tab_id, space_id}`; `space.changed {space}` carries the space whenever its `tabs` order or `active_tab` changed (a tab created, closed, moved or focused).

## Attach

The server keeps a headless terminal (an `alacritty_terminal` grid with a scrollback of `POIMEN_SCROLLBACK` lines, default 10000) per terminal, fed from the PTY, so a client can attach at any time and see the current state. Live output is not rendered by the server: it is passed on as raw bytes, the grid is only read to build the snapshot.

`terminal.attach` is sent on a connection of its own (not a short-lived one). Its result, `AttachResult`:

`{"terminal_id": "t2", "seq": 17, "cols": 80, "rows": 24, "mode": "observe", "snapshot": "<base64>"}`

`snapshot` is the base64 of a byte stream. Written to a fresh emulator of `cols` x `rows` (xterm.js) it restores the screen and scrollback, the cursor (position, shape, visibility), the SGR pen, the scroll region, the title and the modes: alternate screen (the primary screen is restored behind it), mouse tracking 1000/1002/1003 with 1005/1006, bracketed paste, application cursor and keypad, focus reporting, autowrap, origin, insert and line-feed modes. Not restored: the kitty keyboard protocol, charsets, a pending wrap at the last column, hyperlinks, and a synchronized update (`?2026`) that is still open.

From then on the connection carries stream records (the events below) and still accepts requests (`terminal.input`, `terminal.resize`). Every `terminal.output` and `terminal.resized` record has a `seq`; the first one after the result is `seq + 1` and they are contiguous. The snapshot is built and the client registered under one lock per terminal, so no byte is lost or repeated between the snapshot and the stream.

- Roles: any number of observers and at most one controller per terminal. `control` while a controller exists fails with `conflict` unless `take_over` is true; then the previous controller receives `terminal.detached` with reason `taken_over`. Observers receive output and resize records, and cannot send input or resize (`not_controller`). The size is the controller's: observers render at the size of the last `terminal.resized` (or `cols`/`rows` of the result).
- Closing the connection detaches. `terminal.detach` does the same from the client's side when it cannot close the connection itself: named pipes have no `shutdown`, so on Windows a thread blocked reading the stream would not wake up. The server answers, ends the attachment and closes the connection, and the blocked read fails. `poimen_client::AttachmentWriter::close` sends it on every platform (and shuts the socket down on Unix). Adding the request is backwards compatible, so the protocol version stays 2. Attach and detach of the controller are published to subscribers as `terminal.controller_attached` and `terminal.controller_detached`, so the server (and tools) know when nobody answers the terminal's queries.
- Backpressure: output is coalesced (what arrives within 4 ms, at most 32 KiB per record). Each client has a bounded queue (128 records); the PTY is never blocked by a client. A client whose queue is full is detached with `terminal.detached` reason `overflow` (a client that does not read at all is cut off after a 5 s write timeout) and must attach again for a fresh snapshot.
- `terminal.detached` (the server ended the attachment: `overflow`, `taken_over`, `closed`) and `terminal.exited` (the process ended, with its exit code; the stream ends after it) are distinct. Attaching to an exited terminal returns the final snapshot, then `terminal.exited`.
- Reference client: `poimen-console attach` (ADR 0006) observes by default, `--control` takes input and sets the PTY size from the local window, `--takeover` sets `take_over`; the local terminal is raw and restored on detach, exit and signals. Detach key `Ctrl+B d`; the terminal keeps running.

## Terminal queries

Programs ask the terminal for its colors (OSC 10, 11, 12 and 4 with `?`), the cursor position (DSR `CSI 6 n`) and its attributes (DA1 `CSI c`, DA2 `CSI > c`). The headless grid of the terminal (`alacritty_terminal`) produces the answers and the server writes them to the PTY, but only while the terminal has no controller. With a controller attached, its xterm.js answers the same bytes (#96) and the server stays silent, so a query never gets two answers; the hand-over is at attach and detach of the controller (observers do not count). What the grid produced while a controller was attached is dropped, never answered late. Colors come from `server.set_colors` (a dark default until the app has sent one); a color the program set itself with OSC 4, 10 or 11 wins. The app sends the active scheme on start and on every scheme change. Adding the request is backwards compatible, so the protocol version stays 2.

## Agent status

Tokens are free-form key/value strings per terminal, with herdr's semantics (`pane report-metadata`, `pane tokens`) so a tool only switches the command: a name is 1 to 32 ASCII letters, digits, `_` or `-`, a report carries at most 16, a `null` value removes the token, `ttl_s` (above 0) expires the tokens that report set after that many seconds, and `terminal.clear_tokens` removes everything one `source` set. A token belongs to the source that set it last. The visible tokens are the `tokens` map of the terminal in `terminal.list` (absent when empty); `terminal.tokens_changed` `{terminal_id, tokens}` carries all of them and is published only when they changed, also when a TTL ran out (the server checks twice a second) and when the process ended (they are cleared with the terminal's exit). The app maps `tokens` to the `tokens` of the pane, so `$<name>` in `sidebar.rows` works as on herdr. The CLI is `poimen-server report tokens|clear|agent` (README, "Tokens from scripts").

Agent status comes from hooks only; the server never reads the screen. A reporter (the Claude Code hook) sends `terminal.report_agent` with a `seq` that increases with every report (the hook uses nanoseconds since the epoch). A report whose `seq` is not above the last accepted one of that terminal is stale: it is dropped and the result is `{"accepted": false}`. `message` is the notification text of the agent (the `message` of Claude Code's permission `Notification`, of Copilot CLI's `notification`); the hooks and the server clean it: control characters become spaces, whitespace collapses, at most 300 characters. The server keeps the latest text with its time (`message`, `message_at` in epoch milliseconds in the terminal's `agent`); a report without `message` leaves it, a `working` report clears it. `status` `gone` means the agent ended and clears the terminal's `agent`. `agent.status_changed` is published only when the state of the terminal actually changed. Adding the request, the `agent` field of Terminal and `session_id` of the event is backwards compatible, so the protocol version stays 2.

On the first start with the poimen backend the app offers to run `integration install` for the agents whose hooks are missing (`status` decides); declining is remembered in the UI state. Claude Code: `poimen-server integration install|uninstall|status claude [--settings <path>]` registers `poimen-server hook claude` in `~/.claude/settings.json` (entries marked with `# poimen-agent-hook`, on rc `poimen-server-rc hook claude` marked `# poimen-rc-agent-hook`, next to existing ones such as herdr's and those of the other channel; install and uninstall touch only the entries of their own channel). `status` counts an entry only while the binary it calls exists, so hooks of a moved binary are offered again. The hook does nothing outside a poimen terminal (neither `POIMEN_TERMINAL_ID` nor `POIMEN_SOCKET` set) and in a terminal of the other channel (`POIMEN_SOCKET` is that channel's default socket; its own hook reports there), reads the first JSON value of stdin without waiting for its end, gives up after 1.5 s and always exits 0. A report that does not get through (only `POIMEN_SOCKET` set, a payload that is not JSON or does not arrive, no server, a terminal the server does not know, a stale report, no answer in time) is one line on stderr and in `hooks.log` next to `server.json` (`$POIMEN_STATE_DIR`, `%LOCALAPPDATA%\poimen-server` on Windows, `-rc` directories on rc; moved to `hooks.log.1` at 256 KiB) with time, version, hook, reason, terminal and socket. Agents read their hooks when they start: one that ran before `integration install` reports nothing until it is started again. Mapping: `SessionStart` idle, `Stop` done (the turn ended; the status stays done until the next prompt, poimen clears the unread mark when the tab is viewed), `UserPromptSubmit` and `PostToolUse` working, `Notification` of type `permission_prompt` blocked, `SessionEnd` gone; events with an `agent_id` (subagents) are ignored.

Copilot CLI: `poimen-server integration install|uninstall|status copilot [--settings <path>]` writes `~/.copilot/hooks/poimen-agent-state.json` (on rc `poimen-rc-agent-state.json` with the rc marker; a file of our own, marked with `# poimen-agent-hook`; an existing file without the marker is never touched), registering `poimen-server hook copilot <event>`. Same hook behavior as for Claude Code. Mapping: `sessionStart` idle, `agentStop` done (same as `Stop`), `userPromptSubmitted` and `postToolUse` working, `notification` of type `permission_prompt` blocked (reported by Copilot CLI 1.0.71), `sessionEnd` gone; subagent events are ignored. Both payload styles are accepted: camelCase (`sessionId`, `notificationType`, event from the command line) and PascalCase names with snake_case fields (`hook_event_name`, `session_id`, `notification_type`).

On Windows the hooks run through PowerShell: Claude Code entries get `"shell": "powershell"` and the command `& '<path of poimen-server.exe>' hook claude # poimen-agent-hook` (single quotes doubled), the Copilot file gets a `powershell` command next to `bash`, and the hook timeout is 5 s instead of 2 (the PowerShell start). A Claude Code without the `shell` field runs the command in Git Bash, where it fails as a non-blocking hook error. `integration status` finds the marker in either form.

Starting an agent and prompting it need no request of their own (`poimen_client::agent`): `start_agent` checks that the terminal has no agent, types the command line (words single-quoted for the terminal's shell, chosen by the `program` of the terminal: POSIX quoting writes an apostrophe as `'\''`, pwsh and powershell double it as `''`; for cmd.exe, which cannot quote arguments safely, nothing is typed and the call fails with a message that says so; empty arguments are dropped) with Enter through `terminal.input` and resolves when the terminal's `agent` appears, i.e. when the `SessionStart` report arrives (30 s, then a timeout error that points to the hooks). `prompt_agent` types the text with Enter, unless the agent is `working` or `blocked` (nothing is typed), and waits up to 10 s for it to report `working` or `blocked`. The `Backend` methods `agent_start`, `agent_prompt` and `agent_rename` of the poimen backend use them; the agent name is the name of its terminal (`terminal.rename`).

## Persistence

The layout (the spaces with id, name, cwd, tab order and active tab; the tabs with their trees; the id counter `next_id`) is stored in `$POIMEN_STATE_DIR/server.json`, else `$XDG_STATE_HOME/poimen/server.json`, else `~/.local/state/poimen/server.json` (Windows: `$POIMEN_STATE_DIR\server.json`, else `%LOCALAPPDATA%\poimen-server\server.json`, else `~\AppData\Local\poimen-server\server.json`), and read at start. On rc the directories are `poimen-rc` and `poimen-server-rc`. Terminals are not persisted: a restarted server starts without terminals, drops the leaves whose terminal is gone, collapses their splits and drops the tabs left empty (once terminals survive a restart, #574, their leaves stay). Every running terminal without a leaf gets a tab of its own, which is how the spaces of a protocol 3 `server.json` (no `tabs`) get one tab per terminal. The id counter is persisted so no id, a dropped `split_id` included, is given twice.

## Lifecycle

The app starts `poimen-server` detached when no server answers and stops it only after the user confirmed: "Restart server" and "Quit poimen and stop server" send `server.shutdown`, closing the app does not. A server that answers `ping` with the right protocol but an older `version` than the one bundled with the app is reported as `outdated` (notice with "Restart server" and "Later"; after the restart the bundled server is started); one with another `protocol` is reported as `incompatible` with the same offer. The app never starts a second server against a taken socket. It looks for the binary next to its own executable first, then on the login-shell `PATH`. Releases ship it as a sidecar (`bundle.externalBin` in `tauri.bundle.conf.json`, built by `scripts/prepare-sidecar.sh` in `release.yml`); a plain `pnpm tauri build` does not, so build it with `cargo build --release -p poimen-server` and put it beside the app. The socket directory must be a real directory owned by the user with mode 0700: the server tightens one it owns and refuses anything else, and the client refuses to connect otherwise (so a `POIMEN_SOCKET` override must point into a private directory). A `server.lock` next to the socket keeps two servers from both judging a socket stale. Compatibility: a client compares `ping.protocol` with the version it was written for.

Windows: the bundled binary is `poimen-server.exe` next to `poimen-app.exe`. The app copies it to `%LOCALAPPDATA%\poimen-server\bin\<app version>\poimen-server.exe` (reused while size and modification time match, copies of other versions removed when not running) and starts that copy, so an update can replace the installed file; when the copy fails it starts the installed one. The start uses `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW | CREATE_BREAKAWAY_FROM_JOB` (own process group, no console window, out of a job object that would kill it with the app), and without `CREATE_BREAKAWAY_FROM_JOB` when the job forbids breaking away. The pipe admits its owner only: a server started elevated (as administrator) is owned by Administrators and refuses a poimen started normally; the app reports that instead of starting a second server. Start poimen normally.

Linux AppImage (`APPIMAGE` or `APPDIR` set): the bundled binary lives in the AppImage's FUSE mount, which moves on every run and ends with the app. The app copies it to `$XDG_DATA_HOME/poimen-server/bin/<app version>/poimen-server` (else `~/.local/share/...`; directories 0700, the copy 0755, reused and cleaned up as on Windows), points the symlink `$XDG_DATA_HOME/poimen-server/bin/poimen-server` at it, and starts that copy. `integration install` runs from there with `POIMEN_HOOK_EXE` set to the symlink, so the hooks call a path that survives restarts and updates (without `POIMEN_HOOK_EXE`, `install` writes the running binary's path). Other Linux packages and macOS start the installed binary as it is.
