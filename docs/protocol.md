# poimen-server protocol

Protocol version: **6** (version 1 had no terminal output; version 2 adds `terminal.attach`, the stream records and the controller rules for `terminal.input` and `terminal.resize`; version 3 adds tokens per terminal: `terminal.report_tokens`, `terminal.clear_tokens`, `tokens` of Terminal and the `terminal.tokens_changed` event; version 4 adds tabs and split trees per space: `tabs` and `active_tab` of Space, Tab and its nodes, the `tab.*` requests, the `tab.*` and `space.changed` events, see Tabs and splits; version 5 adds the trust handshake of `space.create`: `layout`, `trust` and `command` and the `trust_required` result, see Space layout and trust, and `layout: false` keeps the empty space of version 4. The app skips its own trust gate on this backend and relies on the handshake, so a version 4 server is incompatible; version 6 adds `space.apply_layout`, the same layout and trust handshake for an existing space, see Space layout and trust. The app rebuilds spaces and opens presets through it on this backend and no longer applies layouts itself, so a version 5 server, which answers it with `unknown_method`, is incompatible).

`poimen-server` is a headless daemon that runs the terminals, so shells and agents keep running when the app closes. Each terminal's PTY and child are owned by a `poimen-pty-host` of its own, which the server reads as a client (ADR 0009, "Host protocol" below). The protocol is client-neutral: no Tauri or app concept appears in it. The wire types live in `src-tauri/crates/poimen-protocol`, a client in `src-tauri/crates/poimen-client`.

## Transport

- NDJSON over a local socket (`interprocess::local_socket`, in `poimen_client::transport`): one JSON object per line, UTF-8, `\n` terminated. On Linux and macOS it is a Unix domain socket at the socket path; on Windows it is the named pipe `\\.\pipe\<socket path>`, and the socket path holds a marker file (`<pid>:<unix nanos>`) so "is a server running?" works the same on both. The pipe's DACL (`D:P(A;;GA;;;SY)(A;;GA;;;OW)`) admits SYSTEM and the owner only, and its buffers are 64 KiB.
- Socket path: `$POIMEN_SOCKET`, else `$XDG_RUNTIME_DIR/poimen/server.sock`, else `<temp dir>/poimen-<user>/server.sock`. Windows: `$POIMEN_SOCKET`, else `%LOCALAPPDATA%\poimen-server\server.sock`, else `<temp dir>\poimen-%USERNAME%\server.sock`. Unix: the directory has mode 0700, the socket 0600. One server per user (it holds `server.lock` next to the socket): a second server on a live socket exits; a stale socket file (Windows: a marker without a pipe) is replaced; anything else at the path is left alone and the server refuses to start.
- Channels: a binary is built for the channel `stable` or `rc` (`POIMEN_CHANNEL` at build time, `poimen_protocol::CHANNEL`; an unknown value fails the build). On `rc` every directory above is named with `-rc` (`$XDG_RUNTIME_DIR/poimen-rc/server.sock`, `<temp dir>/poimen-rc-<user>/server.sock`, `%LOCALAPPDATA%\poimen-server-rc\server.sock`), so a stable and an rc server run side by side, one per user and channel. The app and the server ignore a `$POIMEN_SOCKET` that is the default socket of the other channel (they were started from a terminal of the other installation) and use their own; `poimen-server report` uses `$POIMEN_SOCKET` as it is, the server of the terminal it runs in.
- Named pipes have no I/O timeouts and no `shutdown`. On Windows a client bounds a request by waiting on a helper thread, and the server's write timeout for a client that stops reading (5 s) applies on Unix only.
- Requests use short-lived connections (connect, one or more requests, close). A connection that sent `events.subscribe` only receives events afterwards.
- A line that is not a request gets an error response and the connection stays open.

## Messages

Request: `{"id": "1", "method": "space.create", "params": {...}}`. `id` is any string chosen by the client; `params` may be omitted when a method has no required parameter.

Response: `{"id": "1", "result": {...}}` or `{"id": "1", "error": {"code": "not_found", "message": "..."}}`. `id` is `null` in an error for a line that could not be parsed.

Event: `{"event": "terminal.exited", "data": {...}}`. Lines with an `event` field are events; all others are responses.

Error codes: `parse_error`, `invalid_request`, `unknown_method`, `invalid_params`, `not_found`, `exited` (the terminal's process has exited), `spawn_failed`, `not_controller`, `conflict`, `internal`.

## Objects

Space: `{"id": "s1", "name": "api", "cwd": "/home/me/api", "tabs": ["tab2", "tab5"], "active_tab": "tab5"}` (`tabs` in order; `active_tab` absent while the space has no tab; both absent from a protocol 3 server).

Tab: `{"tab_id": "tab2", "space_id": "s1", "name": "zsh", "root": Node, "active_terminal": "t3"}`. `active_terminal` is the focused leaf of the tab.

Node: `{"kind": "terminal", "terminal_id": "t3"}` or `{"kind": "split", "split_id": "split7", "direction": "right" | "down", "ratio": 0.5, "children": [Node, Node]}`. `right` puts the second child right of the first, `down` below it; `ratio` is the share of the first child, above 0 and below 1. `split_id` is assigned by the server, unique within it and stable for the life of the split; it is persisted with the tree and never given to another node, also across restarts.

Terminal: `{"id": "t2", "space_id": "s1", "name": "zsh", "cwd": "...", "cols": 80, "rows": 24, "status": "running" | "exited", "exit_code": 0, "program": "/bin/zsh", "args": ["-l"]}` (`exit_code` only when exited; `program` is the program the terminal runs, absent from older servers; `args` the arguments after it, omitted when empty and from older servers; `survives_restart: true` when the terminal runs in a `poimen-pty-host` that a restarted server adopts, see Persistence, absent from servers that end their terminals on a restart; `host_version` is the version of the `poimen-pty-host` the terminal runs in and `host_bundled_version` the one this server ships with, both absent from servers before #606 and from exited terminals: a host is not updated with the server, so the first can be older than the second, and the app marks such a terminal and offers a restart, a new terminal with the same cwd, program, arguments and place through `tab.split` and `terminal.close`; additive, the protocol version stays 6) `agent` (`{"status": "idle" | "working" | "blocked" | "done", "agent": "claude", "session_id": "..."}`; `agent` and `session_id` optional) is present while hooks report an agent in the terminal, and cleared when it ends or the process exits.

The server owns the tabs and the split tree of each space, so every client shows the same layout (ADR 0006); editor groups and app-only tabs stay the client's business. Terminal ids are unique per server run; ids of spaces, tabs and splits survive restarts.

## Tabs and splits

Every space has its tabs in order (`Space.tabs`), each with a split tree of terminals. The tree and the terminal set never disagree: every leaf is a running terminal and every running terminal is in exactly one leaf. A change of the layout and its events are made under the same lock as the terminal change that caused it, so a subscriber sees `terminal.created` before the tab that holds it, and `terminal.closed` or `terminal.exited` before the tab without it.

- `terminal.create` gives the terminal a tab of its own, so clients that know nothing of tabs keep working. A new tab goes last and becomes `active_tab` only when the space had none.
- Closing or the exit of a terminal removes its leaf: the leaf's sibling takes the parent's place (the split goes with its `split_id`). When the leaf was the tab's `active_terminal`, the first leaf of the node that took the place becomes active. The last terminal of a tab closes the tab; when it was the `active_tab`, the tab that took its place (else the one before it) becomes active.
- Splits are addressed by `split_id`, never by a path in the tree: clients change the same tree at the same time, and a path shifts when another client splits or closes a pane.
- Focus is shared: `active_tab` and `active_terminal` change only through `tab.focus` (or when the focused tab or leaf goes away), and the last client that sends `tab.focus` wins. A client that only views a tab does not send it.

Events: `tab.created {tab}`, `tab.changed {tab}` (the full tab after any change of its tree, name, place in the order or focus) and `tab.closed {tab_id, space_id}`; `space.changed {space}` carries the space whenever its `tabs` order or `active_tab` changed (a tab created, closed, moved or focused).

## Space layout and trust

`space.create` with `layout` (the default) builds the new space in the server, so every client gets the same layout. `cwd` must be an existing directory (else `invalid_params`).

- The layout comes from, in order: the `layout` of the project file `.poimen/config.json` of the repository root of `cwd` (`git rev-parse --show-toplevel`, else `cwd`), the deprecated `.agents/herdr-layout.json`, the `layout` of the matching space template (`spaceTemplates` of the user config), `spaces.layout` of the user config, the built-in default (`poimen_core::layout::resolve`). `command` replaces the command of the root pane (a task's command); else the matching template's agent fills a root pane without a command of its own.
- The first pane is the root of the space's first tab (named like the pane, the space's `active_tab`); every later pane splits its `split.from` with its `direction` and `ratio` (the split pane keeps `ratio`). Each pane is a terminal with the default shell in `cwd`, named like the pane; its `command` is typed into the shell followed by Enter (`\r`). The project's `setup` gets a tab of its own named `setup` after the layout, its command typed the same way (`setup_started`).
- An invalid project layout is a warning, and the space gets one pane; a pane that cannot be made stops the layout with a warning, and the space keeps what was built. `warnings` lists them.
- The user config is `~/.config/poimen/config.json` (rc: `~/.config/poimen-rc/config.json`), read again for every `space.create`: `trustedProjects`, `spaceTemplates`, `spaces.layout`, `harnesses`.

Trust handshake: the project files are read once; the trust hash (SHA-256 of their content), the listed commands and the layout all come from that read. When they contain commands and `trustedProjects` of the user config (the only source of trust) has another hash for the root, the result is `{trust_required: {root, files, hash, commands: [{what, command}], layout?}}` (`layout`: the panes that would be built, `[{name, command?, split?: {from, direction, ratio}}]`, absent when the project layout is invalid), and nothing is created, run or stored. The client asks the user and sends `space.create` again with `trust`:

- `{"kind": "trust", "hash": "..."}` (the `hash` of the question): when it is still the hash of the files as read now, the server stores it in `trustedProjects` (writing only that key of `config.json`, keeping every other key and comment) and builds the space with the commands; a hash that no longer matches gets a new `trust_required`.
- `{"kind": "without"}`: the space gets the panes and splits of the project layout without its commands, and no `setup`; nothing is stored, and the next `space.create` asks again.

`space.apply_layout` builds into an existing space with the same rules: the project files of the repository root of `cwd` are read once, the same `trust_required` (with `layout` the panes of the resolved layout or of the preset) comes back with nothing created, and the client sends it again with `trust`. Its root pane opens a new tab at the end of the space (the space's `active_tab` only when it had none), every later pane splits its `from` (`tab.changed` for each split), and the `setup` tab follows only without `preset`. A preset is `presets[]` of `.poimen/config.json`; its commands are project commands, typed only when trusted (`without`: its panes without them). An invalid or unknown preset is `not_found` before anything is asked or stored.

## Attach

The server keeps a headless terminal (an `alacritty_terminal` grid with a scrollback of `POIMEN_SCROLLBACK` lines, default 10000) per terminal, fed from the terminal's host, so a client can attach at any time and see the current state. Live output is not rendered by the server: it is passed on as raw bytes, the grid is only read to build the snapshot.

`terminal.attach` is sent on a connection of its own (not a short-lived one). Its result, `AttachResult`:

`{"terminal_id": "t2", "seq": 17, "cols": 80, "rows": 24, "mode": "observe", "snapshot": "<base64>"}`

`snapshot` is the base64 of a byte stream. Written to a fresh emulator of `cols` x `rows` (xterm.js) it restores the screen and scrollback, the cursor (position, shape, visibility), the SGR pen, the scroll region, the title and the modes: alternate screen (the primary screen is restored behind it), mouse tracking 1000/1002/1003 with 1005/1006, bracketed paste, application cursor and keypad, focus reporting, autowrap, origin, insert and line-feed modes. Not restored: the kitty keyboard protocol, charsets, a pending wrap at the last column, hyperlinks, and a synchronized update (`?2026`) that is still open.

From then on the connection carries stream records (the events below) and still accepts requests (`terminal.input`, `terminal.resize`). Every `terminal.output` and `terminal.resized` record has a `seq`; the first one after the result is `seq + 1` and they are contiguous. The snapshot is built and the client registered under one lock per terminal, so no byte is lost or repeated between the snapshot and the stream.

- Roles: any number of observers and at most one controller per terminal. `control` while a controller exists fails with `conflict` unless `take_over` is true; then the previous controller receives `terminal.detached` with reason `taken_over`. Observers receive output and resize records, and cannot send input or resize (`not_controller`). The size is the controller's: observers render at the size of the last `terminal.resized` (or `cols`/`rows` of the result).
- Closing the connection detaches. `terminal.detach` does the same from the client's side when it cannot close the connection itself: named pipes have no `shutdown`, so on Windows a thread blocked reading the stream would not wake up. The server answers, ends the attachment and closes the connection, and the blocked read fails. `poimen_client::AttachmentWriter::close` sends it on every platform (and shuts the socket down on Unix). Adding the request is backwards compatible, so the protocol version stays 2. Attach and detach of the controller are published to subscribers as `terminal.controller_attached` and `terminal.controller_detached`, so the server (and tools) know when nobody answers the terminal's queries.
- Backpressure: output is coalesced (what arrives within 4 ms, at most 32 KiB per record). Each client has a bounded queue (128 records); the PTY is never blocked by a client, nor by the server: the host does not wait for the server, which reads it into a queue of up to 64 MiB while its grid catches up (past that the host drops the connection and the server attaches again after the last `seq` it read, with a `gap` when the host's ring has moved on). A client whose queue is full is detached with `terminal.detached` reason `overflow` (a client that does not read at all is cut off after a 5 s write timeout) and must attach again for a fresh snapshot.
- `terminal.detached` (the server ended the attachment: `overflow`, `taken_over`, `closed`) and `terminal.exited` (the process ended, with its exit code; the stream ends after it) are distinct. Attaching to an exited terminal returns the final snapshot, then `terminal.exited`.
- Reference client: `poimen attach` (ADR 0006; `poimen ls|status|new|send|prompt` are the single-request commands over `poimen-client`) observes by default, `--control` takes input and sets the PTY size from the local window, `--takeover` sets `take_over`; the local terminal is raw and restored on detach, exit and signals. Detach key `Ctrl+B d`; the terminal keeps running.

## Terminal queries

Programs ask the terminal for its colors (OSC 10, 11, 12 and 4 with `?`), the cursor position (DSR `CSI 6 n`) and its attributes (DA1 `CSI c`, DA2 `CSI > c`). The headless grid of the terminal (`alacritty_terminal`) produces the answers and the server writes them to the PTY, but only while the terminal has no controller. With a controller attached, its xterm.js answers the same bytes (#96) and the server stays silent, so a query never gets two answers; the hand-over is at attach and detach of the controller (observers do not count). What the grid produced while a controller was attached is dropped, never answered late. Colors come from `server.set_colors` (a dark default until the app has sent one); a color the program set itself with OSC 4, 10 or 11 wins. The app sends the active scheme on start and on every scheme change. Adding the request is backwards compatible, so the protocol version stays 2.

## Agent status

Tokens are free-form key/value strings per terminal, with herdr's semantics (`pane report-metadata`, `pane tokens`) so a tool only switches the command: a name is 1 to 32 ASCII letters, digits, `_` or `-`, a report carries at most 16, a `null` value removes the token, `ttl_s` (above 0) expires the tokens that report set after that many seconds, and `terminal.clear_tokens` removes everything one `source` set. A token belongs to the source that set it last. The visible tokens are the `tokens` map of the terminal in `terminal.list` (absent when empty); `terminal.tokens_changed` `{terminal_id, tokens}` carries all of them and is published only when they changed, also when a TTL ran out (the server checks twice a second) and when the process ended (they are cleared with the terminal's exit). The app maps `tokens` to the `tokens` of the pane, so `$<name>` in `sidebar.rows` works as on herdr. The CLI is `poimen-server report tokens|clear|agent` (README, "Tokens from scripts").

Agent status comes from hooks only; the server never reads the screen. A reporter (the Claude Code hook) sends `terminal.report_agent` with a `seq` that increases with every report (the hook uses nanoseconds since the epoch). A report whose `seq` is not above the last accepted one of that terminal is stale: it is dropped and the result is `{"accepted": false}`. `message` is the notification text of the agent (the `message` of Claude Code's permission `Notification`, of Copilot CLI's `notification`); the hooks and the server clean it: control characters become spaces, whitespace collapses, at most 300 characters. The server keeps the latest text with its time (`message`, `message_at` in epoch milliseconds in the terminal's `agent`); a report without `message` leaves it, a `working` report clears it. `status` `gone` means the agent ended and clears the terminal's `agent`. `agent.status_changed` is published only when the state of the terminal actually changed. Adding the request, the `agent` field of Terminal and `session_id` of the event is backwards compatible, so the protocol version stays 2.

On the first start with the poimen backend the app offers to run `integration install` for the agents whose hooks are missing (`status` decides); declining is remembered in the UI state. Claude Code: `poimen-server integration install|uninstall|status claude [--settings <path>]` registers `poimen-server hook claude` in `~/.claude/settings.json` (entries marked with `# poimen-agent-hook`, on rc `poimen-server-rc hook claude` marked `# poimen-rc-agent-hook`, next to existing ones such as herdr's and those of the other channel; install and uninstall touch only the entries of their own channel). `status` counts an entry only while the binary it calls exists, so hooks of a moved binary are offered again. The hook does nothing outside a poimen terminal (neither `POIMEN_TERMINAL_ID` nor `POIMEN_SOCKET` set) and in a terminal of the other channel (`POIMEN_SOCKET` is that channel's default socket; its own hook reports there), reads the first JSON value of stdin without waiting for its end, gives up after 1.5 s and always exits 0. A report that does not get through (only `POIMEN_SOCKET` set, a payload that is not JSON or does not arrive, no server, a terminal the server does not know, a stale report, no answer in time) is one line on stderr and in `hooks.log` next to `server.json` (`$POIMEN_STATE_DIR`, `%LOCALAPPDATA%\poimen-server` on Windows, `-rc` directories on rc; moved to `hooks.log.1` at 256 KiB) with time, version, hook, reason, terminal and socket. Agents read their hooks when they start: one that ran before `integration install` reports nothing until it is started again. Mapping: `SessionStart` idle, `Stop` done (the turn ended; the status stays done until the next prompt, poimen clears the unread mark when the tab is viewed), `UserPromptSubmit` and `PostToolUse` working, `Notification` of type `permission_prompt` blocked, `SessionEnd` gone; events with an `agent_id` (subagents) are ignored.

Copilot CLI: `poimen-server integration install|uninstall|status copilot [--settings <path>]` writes `~/.copilot/hooks/poimen-agent-state.json` (on rc `poimen-rc-agent-state.json` with the rc marker; a file of our own, marked with `# poimen-agent-hook`; an existing file without the marker is never touched), registering `poimen-server hook copilot <event>`. Same hook behavior as for Claude Code. Mapping: `sessionStart` idle, `agentStop` done (same as `Stop`), `userPromptSubmitted` and `postToolUse` working, `notification` of type `permission_prompt` blocked (reported by Copilot CLI 1.0.71), `sessionEnd` gone; subagent events are ignored. Both payload styles are accepted: camelCase (`sessionId`, `notificationType`, event from the command line) and PascalCase names with snake_case fields (`hook_event_name`, `session_id`, `notification_type`).

On Windows the hooks run through PowerShell: Claude Code entries get `"shell": "powershell"` and the command `& '<path of poimen-server.exe>' hook claude # poimen-agent-hook` (single quotes doubled), the Copilot file gets a `powershell` command next to `bash`, and the hook timeout is 5 s instead of 2 (the PowerShell start). A Claude Code without the `shell` field runs the command in Git Bash, where it fails as a non-blocking hook error. `integration status` finds the marker in either form.

Starting an agent and prompting it need no request of their own (`poimen_client::agent`): `start_agent` checks that the terminal has no agent, types the command line (words single-quoted for the terminal's shell, chosen by the `program` of the terminal: POSIX quoting writes an apostrophe as `'\''`, pwsh and powershell double it as `''`; for cmd.exe, which cannot quote arguments safely, nothing is typed and the call fails with a message that says so; empty arguments are dropped) with Enter through `terminal.input` and resolves when the terminal's `agent` appears, i.e. when the `SessionStart` report arrives (30 s, then a timeout error that points to the hooks). `prompt_agent` types the text with Enter, unless the agent is `working` or `blocked` (nothing is typed), and waits up to 10 s for it to report `working` or `blocked`. The `Backend` methods `agent_start`, `agent_prompt` and `agent_rename` of the poimen backend use them; the agent name is the name of its terminal (`terminal.rename`).

## Runs

A subscription with `run_events` (#692; the app's connection to a machine of `machines[]` asks for it) gets the progress events of the agent runs in the repositories of the server's spaces, so the app shows the runs of a remote machine in its Deliver panel and Events tab like local ones. The files are those of the agent-events `jsonl-file` binding: `<git-common-dir>/.agents/events/<run>.jsonl` (ADR 0002 of GravionLabs/skills; the run id is the file name, `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`, other names are ignored; regular files up to 16 MiB; a file not modified for 25 h is not read). The repositories are those of the space directories and of the running terminals' directories (`git rev-parse --show-toplevel --git-common-dir`, a linked worktree counts as its main repository; `root` is the toplevel of the first directory of it, a path on the server's machine).

- `events` holds complete lines only, each a JSON object, unchanged and in file order (a line that is not a JSON object is skipped; a half-written last line waits until it ends with a newline). Events of an unknown `v` are passed on too; the server does not fold them, the client's reducer of the agent-events core does. At most 500 events per line; a long run takes several.
- Replay: a new subscription first gets every event of the followed runs from the start (one `run.events` per run and chunk), then each new event once. A client that subscribes again (a reconnect) gets the replay again and drops what it folded already by `(run, seq)`.
- The server reads the event directories every 500 ms while at least one subscription asked for `run_events` and keeps the events of the followed files in memory; without such a subscription it reads nothing and drops them. A file that is truncated is read again from its start; a removed file and a repository that is no longer among the spaces' are no longer followed. The server never writes an event file.

## Agent transcripts

`agent.transcript` (#698) lets a client show the flow and the subagent output of an agent in a terminal of another machine, whose transcript files only that machine's server can read. The agent and its session id are those the hooks reported (`agent` and `session_id` of the terminal, `claude` or `copilot`); Claude Code's transcript is found by the terminal's `cwd`: `~/.claude/projects/<cwd with every non-alphanumeric character as "-">/<session>.jsonl`, Copilot CLI's by the session id: `~/.copilot/session-state/<session>/events.jsonl`, both below the home of the server's user. The session id must match `[A-Za-z0-9_-]+`. The server only reads.

- The server keeps a reader per `(terminal_id, follower)`. The first request of a `follower`, one with `restart: true`, one after the terminal's session id changed and one after the server lost the reader (it keeps at most 64; a restart loses all) create it: `fresh` is `true` and `updates` start at the beginning of the transcript. Every later request returns only what the files gained since. A client that sees `fresh` where it expected a continuation has already shown the early updates and should start its view over. Readers of terminals that are gone are dropped.
- `state`: `ok` (followed; `session` names the session of `updates`), `no_agent` (no agent with a readable transcript reported in the terminal, or an unusable session id, or Claude Code without a `cwd`), `missing` (a session is reported but its file is not there yet, or the server has no home; ask again later) or `unreadable` (the file is there but cannot be opened; `reason` says why). Only `ok` has `updates`.
- Each update is an object with a `kind`: `list` (`agents`: the subagents with `agent_id`, `agent_type`, `description`, `tool_use_id`, `spawn_depth`, `worktree_branch`, `status` `running` or `done`, `started`, `last`), `entries` (`agent_id` and the new messages `entries` of that subagent) or `main` (`calls`: the Skill and Agent calls of the main agent with their results, `tools`: the count of other tool calls, `usage`: one token sample per assistant message). These are the shapes of the app's `subagents` event; Copilot's log is mapped onto them. Clients treat unknown fields and kinds as absent.

## Persistence

The layout (the spaces with id, name, cwd, tab order and active tab; the tabs with their trees; the id counter `next_id`) and the list of running terminals (`terminals`, below) are stored in `$POIMEN_STATE_DIR/server.json`, else `$XDG_STATE_HOME/poimen/server.json`, else `~/.local/state/poimen/server.json` (Windows: `$POIMEN_STATE_DIR\server.json`, else `%LOCALAPPDATA%\poimen-server\server.json`, else `~\AppData\Local\poimen-server\server.json`), and read at start. On rc the directories are `poimen-rc` and `poimen-server-rc`. The id counter is persisted so no id, a dropped `split_id` included, is given twice.

Terminals survive a server restart or crash in their `poimen-pty-host` (ADR 0009, #604). Each entry of `terminals` is `{"id", "space_id", "name", "cwd", "program"?, "cols", "rows", "endpoint", "seq", "agent"?, "agent_seq"?, "tokens"?}`: the host's `endpoint`, the `seq` of the last output record read from it, the size last set (the controller's; the controller itself is a connection and attaches again), the agent status as `terminal.report_agent` left it with its `agent_seq` (so a stale report stays dropped; hooks overwrite it as before) and the tokens with their `source` and the end of their TTL as `expires_at_ms` (epoch ms). Exited terminals are not listed. The file is written atomically (temp file, then rename) on every change of a terminal that matters (create, close, exit, rename, resize, an accepted agent report, a token change or expiry, and every layout change) and before `server.shutdown` with `keep_terminals`; the `seq` goes along with these writes, so a crash loses at most the last change. A file without `terminals` (a server before #604) loads with none.

At start the server adopts the listed terminals before it serves: it connects to every host at once, reads its `hello` (5 s each) and attaches with `since: 0`, so the grid is rebuilt from the host's ring. The records up to the `hello`'s `seq` are a replay: grid and attached clients get them, but the terminal queries in them are not answered again (live output after them is answered as usual). A `gap` (the ring moved past records the server never read) becomes one marker line in the grid, `[poimen: earlier output lost, <n> records left the host's buffer]`, after a line break when output came before; a gap a reattach repeats is not marked twice. Name, size (the `hello`'s PTY size), agent status, its `seq` and the tokens come back; a token whose TTL ran out meanwhile is dropped. A terminal keeps its id, so tabs, splits and the app's editor tabs still point to it, and it reports `survives_restart: true`. A host that does not answer, answers with another `hello` (a `seq` behind the one read from it: another host) or whose space is gone (its host is sent `kill`) is dropped with a line on stderr (`poimen-server: dropping terminal <id> (<endpoint>): <reason>`). Then the leaves of terminals that did not come back leave the tree, their splits collapse and tabs left empty are dropped (#510); every running terminal without a leaf gets a tab of its own, which is how the spaces of a protocol 3 `server.json` (no `tabs`) get one tab per terminal. A terminal is adopted by at most one server: only the server holding the socket's lock starts, a host serves one client at a time (a second server's connection `replaced` the first's), and a server that let its hosts go with `keep_terminals` never writes `server.json` again. Clients see the old server's connections end without a record and attach again with `terminal.attach` (the app retries for about 30 s, read-only meanwhile, in the mode it had, never with a takeover).

## Lifecycle

The app starts `poimen-server` detached when no server answers and stops it only after the user confirmed: "Restart server" sends `server.shutdown` with `keep_terminals` (the terminals keep running and the bundled server adopts them; the confirmation names only the terminals without `survives_restart`, which a server before #604 ends), "Quit poimen and stop server" sends it without and ends every terminal; closing the app does not stop the server. A server that answers `ping` with the right protocol but an older `version` than the one bundled with the app is reported as `outdated` (notice with "Restart server" and "Later"; after the restart the bundled server is started); one with another `protocol` is reported as `incompatible` with the same offer. The app never starts a second server against a taken socket. It looks for the binary next to its own executable first, then on the login-shell `PATH`. The server looks for `poimen-pty-host` (`poimen-pty-host-rc` on rc) next to its own executable and nowhere else; without it `terminal.create` (and every space, split, task or setup that needs a terminal) fails with `spawn_failed` "poimen-pty-host is missing: <path> (it ships next to poimen-server)", never with a terminal of the server's own. Releases ship both as sidecars (`bundle.externalBin` in `tauri.bundle.conf.json`, built by `scripts/prepare-sidecar.sh` in `release.yml`); a plain `pnpm tauri build` does not, so build them with `cargo build --release -p poimen-server -p poimen-pty-host` and put them beside the app. The socket directory must be a real directory owned by the user with mode 0700: the server tightens one it owns and refuses anything else, and the client refuses to connect otherwise (so a `POIMEN_SOCKET` override must point into a private directory). A `server.lock` next to the socket keeps two servers from both judging a socket stale. Compatibility: a client compares `ping.protocol` with the version it was written for.

Windows: the bundled binary is `poimen-server.exe` next to `poimen-app.exe`. The app copies it, and the `poimen-pty-host.exe` next to it, to `%LOCALAPPDATA%\poimen-server\bin\<app version>\` (reused while size and modification time match, copies of other versions removed when not running) and starts that copy, so an update can replace the installed file; when the copy fails it starts the installed one. The start uses `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW | CREATE_BREAKAWAY_FROM_JOB` (own process group, no console window, out of a job object that would kill it with the app), and without `CREATE_BREAKAWAY_FROM_JOB` when the job forbids breaking away. The pipe admits its owner only: a server started elevated (as administrator) is owned by Administrators and refuses a poimen started normally; the app reports that instead of starting a second server. Start poimen normally.

Linux AppImage (`APPIMAGE` or `APPDIR` set): the bundled binary lives in the AppImage's FUSE mount, which moves on every run and ends with the app. The app copies it (with the `poimen-pty-host` next to it) to `$XDG_DATA_HOME/poimen-server/bin/<app version>/poimen-server` (else `~/.local/share/...`; directories 0700, the copy 0755, reused and cleaned up as on Windows), points the symlink `$XDG_DATA_HOME/poimen-server/bin/poimen-server` at it, and starts that copy. `integration install` runs from there with `POIMEN_HOOK_EXE` set to the symlink, so the hooks call a path that survives restarts and updates (without `POIMEN_HOOK_EXE`, `install` writes the running binary's path). Other Linux packages and macOS start the installed binary as it is.

## Remote hosts: `poimen-server stdio`

`poimen-server stdio` connects its stdin and stdout to the user's running server on its socket, so `ssh host poimen-server stdio` speaks this protocol over SSH. It starts the server detached (own process group, no terminal) when none answers, waits up to 10 s for it, and uses a running server as it is: it never stops, restarts or replaces one. The bridge copies bytes unchanged in both directions (no parsing, no reframing); it is one connection like any other client's, so `events.subscribe` and `terminal.attach` work through it. When stdin closes (or the SSH session drops) the server gets end of file and may still answer for up to 2 s; then only the bridge ends, the server and its terminals keep running.

The app reaches a machine of `machines[]` this way (`src-tauri/src/machines.rs`): `ssh -T -o BatchMode=yes -o ConnectTimeout=10 -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -- <target> poimen-server stdio` (`poimen-server-rc` on rc), one ssh process per connection. Its first connection sends `ping` and, when the protocol matches, `events.subscribe` (with `client` and `run_events`) on the same connection; the end of that connection is the machine going offline. A server of another protocol gets nothing after the `ping`.

`poimen-server --version` prints `poimen-server <version> (protocol <n>)`, which a machine check reads. Releases attach static musl builds as `poimen-server-<version>-x86_64-unknown-linux-musl.tar.gz` and `poimen-server-<version>-aarch64-unknown-linux-musl.tar.gz` (the archive holds the `poimen-server` binary and the `poimen-pty-host` it starts its terminals in, `poimen-pty-host-rc` on rc; keep them in one directory).

## Host protocol

`poimen-pty-host` (ADR 0009, crate `src-tauri/crates/poimen-pty-host`) owns one terminal: it creates the PTY (`portable-pty`, ConPTY through the vendored copy on Windows), spawns the child and holds both until the child exits, so a server can end and a new one can take the terminal over. It never interprets output: no emulation, spaces, agent status or tokens; it forwards and buffers bytes. On Windows its ConPTY is created without `PSEUDOCONSOLE_INHERIT_CURSOR`: with it conhost asks for the cursor position at start and holds the child back until a reply that the host, which answers no query, never sends. The server is its client (below, "Server as client"). Host protocol version: **1** (`poimen_protocol::host::HOST_VERSION`, reported in `hello`). The wire types are `poimen_protocol::host`.

- Compatibility: the host protocol only changes in a backwards compatible way, since a host is not updated with the server and a new server must speak every host version it can meet. Unknown fields are ignored and an unknown `type` parses as `Unknown` on both sides (the host answers it with `error`, a client skips it).
- Start: the server runs `poimen-pty-host` without arguments and writes one line to its stdin, `HostStart`: `{"endpoint": "<path>", "spawn": {"argv": ["sh"], "cwd": "/w", "env": {"POIMEN_TERMINAL_ID": "t3"}, "cols": 80, "rows": 24}, "orphan_timeout_ms": 86400000, "ring_bytes": 1048576, "exit_linger_ms": 30000}`. `spawn` is the `SpawnSpec`: `argv` (never empty), `cwd`, `env` (set on top of the host's own environment; optional) and the size. The last three fields are optional with the defaults shown (24 h, 1 MiB, 30 s). The host binds the endpoint, spawns the child and answers with one line on stdout: `hello` (below), or `{"type": "error", "message": "..."}` and exit code 1 (empty `argv`, endpoint taken or not bindable, program not startable; the endpoint is removed again). `poimen-pty-host --version` prints `poimen-pty-host <version> (host protocol <n>)`; an unknown argument exits 2.
- Endpoint: per host, at the path the server passes, with the transport of the server (`poimen_client::transport`): a Unix socket (mode 0600) or the named pipe `\\.\pipe\<path>` with its marker file and the owner-only DACL on Windows. The host removes the entry when it ends.
- Messages: NDJSON as above, each with a `type`. Host to client:
  - `{"type": "hello", "host_version": 1, "version": "0.16.0", "pid": 4100, "child_pid": 4101, "size": {"cols": 80, "rows": 24}, "endpoint": "<path>", "seq": 17}`: the first line of every connection (and of stdout at start). `seq` is the latest output record (0: none yet), `size` the current PTY size.
  - `{"type": "output", "seq": 18, "bytes": "<base64>"}`: PTY output exactly as read. `seq` starts at 1, rises by one per record, and is never reset while the host runs.
  - `{"type": "gap", "from": 1, "to": 9}`: records `from..=to` have left the ring; sent before the replay.
  - `{"type": "exit", "code": 0}`: the child ended (`code` `null` when unknown), after all its output; the connection and the host end after it.
  - `{"type": "replaced"}`: another client connected; this connection ends.
  - `{"type": "error", "message": "..."}`: a line could not be handled; the connection stays.
- Client to host:
  - `{"type": "attach", "since": 17}`: starts the output stream after record `since` (default 0: the whole ring): a `gap` when the ring has moved past `since + 1`, the records of the ring after `since`, then live output, and `exit` when the child has ended. Before `attach` a connection gets no output. A `since` above the host's `seq` (another host) and a second `attach` are answered with `error`.
  - `{"type": "input", "bytes": "<base64>"}`, `{"type": "resize", "cols": 100, "rows": 30}` (at least 1x1): to the PTY.
  - `{"type": "kill"}`: ends the child (SIGHUP on Unix, `TerminateProcess` on Windows); the host sends `exit` and ends. A child that is still there after 5 s is left to the PTY's hangup when the host ends.
- Output ring: the latest output records, at most `ring_bytes` bytes (default 1 MiB) and 16384 records; the newest is always kept. Output read while no client is attached goes only there.
- One client at a time: a new connection replaces the current one (the old server is gone or going), which gets `replaced`. The host is never blocked by its client: the client's queue holds 1024 records, a client that falls behind is disconnected and reconnects with `since`; a client that does not read is cut off after 5 s (Unix; on Windows, where a pipe has no `shutdown`, its stream only stops until it closes the connection).
- Lifetime: the host ends with its child (once a client got `exit`, else after `exit_linger_ms` without a client collecting it), after `kill`, and after `orphan_timeout_ms` without any connection (it kills the child first). Any connection, attached or not, holds off the orphan timeout.
- Server as client (#603): `terminal.create` (and every caller: `space.create`, `space.apply_layout`, `tab.split`, tasks, setup) starts the host of the new terminal (`poimen-pty-host` next to the server, own process group, stderr discarded; reaped by the server) with the endpoint `hosts/<terminal id>` next to the server's socket (directory 0700; a stale entry there is removed), the command as `argv`, the terminal's `cwd` and size, and `env` `POIMEN_SOCKET`, `POIMEN_TERMINAL_ID` and `TERM=xterm-256color` when the server has no `TERM` or a dumb one. It waits up to 10 s for `hello` on stdout; an `error` line is the message of `spawn_failed`. Then it connects, reads `hello`, attaches with `since: 0` and keeps the endpoint and the last `seq` it read per terminal. Records are taken strictly by `seq`: one at or below the last read is dropped, so no byte reaches the grid twice. Output is coalesced and fed to the grid and the attached clients as before; `terminal.input`, `terminal.resize`, the answers to terminal queries and the commands typed by a layout are `input`/`resize` lines, written whole and in order by one thread per terminal without a write timeout (so the connection never holds half a line; a request never waits for the host: a resize replaces the pending size, `terminal.input` waits only while 1 MiB of input is queued); `terminal.close` and `server.shutdown` send `kill` on a connection of their own, so it never waits behind input the child does not read (the host takes that connection as its client and ends). `exit` ends the terminal with its code after its output; a connection that ends without `exit` is attached again after the last `seq` read, and when the host no longer answers (or keeps dropping the connection without new records, or another client took it over with `replaced`) the terminal ends as an exit without a code. Either way the terminal leaves its tree and the events are those of an exit (`terminal.exited`, then `tab.*`). A restarted or crashed server's hosts are adopted by the next one (#604, see Persistence); a host no server comes back for ends with the orphan timeout.
