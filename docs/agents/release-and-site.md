# Updater and site

Self-update and the public site. Read before you touch these areas. Notes on a change go here, not in `AGENTS.md`.

- `src-tauri/src/updater.rs`: self-update through `tauri-plugin-updater` (`update_check`, `update_install`; a failed install keeps the update pending; `enabled(CHANNEL)`: an rc build registers no plugin and hides the update item). Only on a user click, no other network call; frontend `core/updater.ts` (`Updater` state over poimen's `HxUpdateBackend`, provided as `HX_UPDATE_BACKEND`; `HxUpdateService` and `HxStatusUpdate` are not used: the service drops the update after a failed install and reads version and channel synchronously; `angular.json` marks the plugin imports of helix's default backend external, no npm plugin is added) and the status bar (`hx-status-item` with `hxStatusPopover`); `main.ts` provides `provideHxAppInfo` from `app_version`/`app_channel` (`core/app-info.ts`); signing and flow in `docs/updater.md`.
- `site/`: the public site on GitHub Pages (`https://gravionlabs.github.io/poimen/`), VitePress, self-contained (own npm lockfile, excluded from the app's oxlint, ESLint and oxfmt). The ADRs of `docs/adr/` are not published there; a dead link fails `npm run build`. Download links are resolved client-side from the latest release (`site/downloads.ts`, tested). Workflow `.github/workflows/pages.yml`: dry-run build on pull requests touching `site/`, deploy on push to `main`; one job calling `GravionLabs/ci` `vitepress-pages.yml@v1` (`site-path: site`, its input `deploy` defaults to `true`).
- **Screenshots (#1109).** `pnpm screenshots [view...] [--out dir]` writes `site/public/screenshots/<view>-<light|dark>.png` without Tauri: headless Chromium (the Playwright setup of `scripts/browser/playwright.mjs`, #1020) opens the app built with `ng build -c demo`, served as `poimen:serve:demo` on port 1422. That configuration swaps `src/app/core/tauri.ts` for `src/demo/tauri.demo.ts` (`fileReplacements`), so a `DemoBridge` answers every command, event, channel and dialog call of `TauriBridge`; it is not in the production bundle. Layout: `src/demo/kit/` is generic (answer registry, event emit, `DemoChannel`, the failure on an unanswered command) and imports nothing from the app; `src/demo/poimen/` has the demo data (`data.ts`, times count back from `NOW`) and the answers (`demo.ts`); `scripts/screenshots/views.mjs` lists the views and the clicks before each. Rules: a command with no answer fails the run and names the command (`window.__demoFailures`), also in a view that swallows the error; the clock is fixed (`TIME`), animation is off (`reducedMotion`), the window is 1280×800, xterm's cursor is hidden by the canned bytes; two runs give identical files (compare with `cmp`). Add a view: put its data in `data.ts`, answers in `demo.ts`, an entry in `views.mjs` that waits for what it shows (`terminalShows` for a terminal: a canvas has no text), run it, look at `tmp/shots/failed-<view>-<theme>.png` when it fails, then use the image in a guide page with `<Screenshot src light>`. Redo the images after every UI change: `pnpm screenshots`, check `git diff --stat site/public/screenshots`, commit. `flow-subagents-*.png` is not produced by the script (a transcript of subagents is not in the demo data yet) and keeps its capture of 4 November. Single components come from `pnpm fixtures:shot` (#1020); use it where a page shows one component.
